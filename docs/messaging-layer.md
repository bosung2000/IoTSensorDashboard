# 통신 층 상세 — 앱이 앱에게 말을 거는 법

> 3층에서 만든 것을 **용어부터** 풀어 쓴다.
> 앞의 두 층이 "한 프로그램 안"의 이야기였다면, 여기부터는 **프로그램 사이**의 이야기다.

---

## 0. 이 층이 정확히 무엇인가

세 개의 프로그램이 **서로를 코드로 참조하지 않으면서** 데이터를 주고받게 만드는 층이다.

| # | 무엇 | 대답하는 질문 |
|---|---|---|
| ① **연결** | 브로커 · TLS · 재연결 | 어떻게 **이어질** 것인가 |
| ② **약속** | 토픽 · QoS · 페이로드 형식 | 무슨 **말**로 주고받을 것인가 |
| ③ **발생원** | 센서 팜 엔진 | 무엇을 **보낼** 것인가 (악조건 포함) |

### 앞 두 층과 결정적으로 다른 점

```
1층 Core     순수 함수        →  몇 밀리초면 검증 끝
2층 Sqlite   파일 하나        →  임시 파일 만들어 검증
3층 Mqtt     진짜 네트워크    →  실제로 브로커를 띄워야 검증됨
```

그래서 이 층에는 **통합 테스트**가 붙는다(§7).

## 1. 기초 — 왜 "직접 부르지" 않고 메시지를 보내나

### 가장 단순한 방법: 직접 호출

```csharp
// 센서 팜이 관제실 함수를 직접 부른다
controlRoom.Ingest(reading);
```

편하다. 그런데 이러면:

- 두 프로그램이 **같은 프로세스**에 있어야 한다 → 사실상 한 프로그램이다
- 관제실이 죽으면 팜도 같이 죽는다
- 나중에 팜을 **다른 기계**로 옮길 수 없다

### 우리 방법: 메시지로만 이어진다

```
[SensorFarm.exe]  ──메시지──▶  [ControlRoom.exe]  ──메시지──▶  [Dashboard.exe]
```

세 앱은 서로의 함수를 모른다. **토픽 문자열**만 안다.

> 🔑 이걸 **느슨한 결합(loose coupling)** 이라 한다.
> 대가는 복잡도(연결이 끊길 수 있다)이고, 얻는 것은 **독립성**이다.
> 프로그램 하나가 죽어도 나머지는 계속 돈다.

## 2. MQTT 기초 용어

### 발행/구독 (pub-sub)

```
   센서 ──발행(publish)──▶  [ 브로커 ]  ──전달──▶  구독자(subscribe)
                            토픽으로 분류
```

| 용어 | 뜻 |
|---|---|
| **브로커(broker)** | 중개자. 메시지를 받아 토픽별로 분류해 전달한다 |
| **발행(publish)** | "이 토픽에 이 내용을 보낸다" |
| **구독(subscribe)** | "이 토픽에 오는 걸 나한테 달라" |
| **토픽(topic)** | 메시지의 주소. 슬래시로 계층을 만든다 |
| **페이로드(payload)** | 메시지 본문. 우리는 JSON 텍스트를 쓴다 |

**보내는 쪽은 누가 받는지 모르고, 받는 쪽은 누가 보내는지 모른다.**
구독자가 하나든 열이든, 나중에 하나 더 붙든 발행 코드는 그대로다.

### 토픽 규약 — 이게 곧 계약이다

```
sensors / flir / g1-s0 / flir-0001
  [0]     [1]     [2]      [3]
          벤더    매장     센서ID
```

| 자리 | 쓰는 곳 |
|---|---|
| `[1]` 벤더 | **코덱 라우팅 키** — 어느 해석기로 보낼지 |
| `[2]` 매장 | **소비 측 집계** — 대시보드가 별도 조회 없이 매장별로 묶을 수 있다 |

> 🔴 이 문자열이 한 글자라도 다르면 앱은 각각 잘 뜨는데 **데이터가 안 흐른다** — 오류 메시지도 없이.
> 그래서 파싱을 Core 에 두고 테스트로 잠갔다.

### 와일드카드

```
sensors/#     sensors 아래 전부 (다단계)
health/ack/#  health/ack 아래 전부
```

### QoS — 어디까지 책임지고 배달할 것인가

| QoS | 하는 일 | 결과 |
|---|---|---|
| **0** | 던지고 잊는다 | 도착 안 해도 아무도 모른다 |
| **1** | 받았다는 답이 올 때까지 재전송 | 반드시 도착 · **중복 가능** |
| **2** | 4단계 왕복으로 중복까지 제거 | 정확하지만 느리다 |

우리 선택:

| 토픽 | QoS | 왜 |
|---|---|---|
| 센서 데이터 | **1** | 유실되면 숫자가 틀린다 |
| 헬스 핑·응답 | **0** | 놓쳐도 2.5초 뒤 다시 묻는다 |

**QoS 2 를 안 쓰는 것**이 이 설계의 요약이다 —
"정확히 1회"를 네트워크에 맡기는 대신 **멱등키로 우리가 접는다.**
중복은 오게 두고, 저장소가 한 건으로 만든다. 1단계 왕복으로 끝난다.

### retain — 우리는 안 쓴다

**retain** = 브로커가 마지막 값을 붙잡고 있다가 새 구독자에게 주는 기능.

🚫 이 시스템에서 그러면 **죽은 센서의 마지막 값이 새 대시보드에 "방금 온 값"처럼** 보인다.
「모르는 것을 아는 것처럼 그리지 마라」에 정면으로 어긋난다.

## 3. 브로커를 앱 안에 넣는다는 것

### 보통은 따로 설치하는 서버 프로그램이다

```
[센서앱]  ─┐
           ├─▶ [Mosquitto.exe]   ← 설치 · 설정 · 서비스 등록
[대시보드] ─┘
```

### 우리는 라이브러리로 가져다 쓴다

```
┌────── ControlRoom.exe (프로세스 하나) ──────┐
│                                              │
│   [브로커]  ← 127.0.0.1:5281 포트를 연다      │
│      │                                       │
│   [수집 · 판정 · 저장]                        │
└──────────────────────────────────────────────┘
        ▲                      ▲
   TCP 접속               TCP 접속
 [SensorFarm.exe]     [Dashboard.exe]
```

**바깥에서 보면 똑같다.** 다른 앱은 그냥 "5281 포트에 TCP 접속"할 뿐이다.

| | 별도 브로커 | 앱 내장 |
|---|---|---|
| 실행 준비 | 설치 → 설정 → 서비스 등록 | **exe 실행** |
| 검증 | 환경이 다르면 결과도 다름 | 어디서 돌려도 같다 |

### 치르는 값 (정직하게)

- **관제실이 죽으면 통신 전체가 끊긴다** → 그래서 나머지는 무한 재시도한다
- **브로커 CPU 를 수집과 나눠 쓴다** → 메시지 1건 비용의 38% 가 브로커 라우팅이다
- 센서가 1만 대를 넘어가면 **브로커를 별도 호스트로 분리**하는 게 첫 번째 개선이다

## 4. TLS 와 인증서

### TLS 가 하는 일 셋

| 기능 | 없으면 |
|---|---|
| **암호화** | 같은 네트워크에서 패킷을 캡처하면 평문 그대로 보인다 |
| **무결성** | 중간에 값이 바뀌어도 모른다 |
| **신원 확인** | 가짜 브로커에 접속해도 모른다 |

### 인증서 = 신분증, 자체서명 = 내가 나에게 발급한 것

```
CA 서명 인증서  :  국가가 발급한 여권   → 남이 검증 가능
자체서명 인증서  :  내가 만든 사원증     → 제3자 검증 불가
```

브라우저의 "이 사이트는 안전하지 않습니다" 경고가 대개 이것이다.
암호화는 되는데 **"이 서버가 진짜인지 증명할 방법이 없어서"** 경고한다.

### 우리가 자체서명으로 괜찮은 이유

**브로커가 `127.0.0.1`(루프백)에만 바인딩되어 있다.**

```
[ 같은 PC 안 ]  SensorFarm ──▶ 127.0.0.1:5281 ──▶ ControlRoom
[ 바깥 ]        다른 PC ──✗── 접속 자체가 불가능
```

통신이 컴퓨터 밖으로 안 나가므로 **중간자가 낄 물리적 자리가 없다.**
인증서의 "신원 확인"이 필요한 이유가 중간자 방지인데, 중간이 없으면 할 일이 없다.

> 🔴 **이건 조건부로 맞는 이야기다.**
> 브로커를 다른 호스트로 분리하는 순간, 검증을 통과시킨 그 코드는 **진짜 취약점**이 된다.
> 그래서 코드 주석과 `spec-gaps.md` G-12 에 "언제 켜야 하는지"를 함께 적었다.

### 🚫 TLS 는 로그인이 아니다

| | 하는 일 | 이번 범위 |
|---|---|---|
| **TLS** | 오가는 내용을 못 읽게 | ✅ |
| **인증** | 접속한 게 누구인지 확인 | 🚫 |
| **인가** | 그 사람이 뭘 해도 되는지 | 🚫 |

지금은 **포트에 접속만 하면 아무 메시지나 발행할 수 있다.**
그걸 막는 건 TLS 가 아니라 **루프백 바인딩**이다.

### ⚠️ 인증서 함정 하나

인증서를 만들 때 **메모리 전용 키**를 쓰면 Windows 의 TLS 구현이 서버 쪽에서 그 키를 못 쓴다.
증상이 오류가 아니라 **"연결이 그냥 끊김"**이라 방화벽·포트를 한참 뒤지게 된다.

→ PFX 형식으로 한 번 내보냈다 다시 읽으면 서버가 쓸 수 있는 형태가 보장된다.

## 5. 새로 나온 프로그래밍 개념

### 비동기 (async / await)

**문제**: 네트워크 작업은 느리다. 응답을 기다리는 동안 프로그램이 멈추면 안 된다.

```csharp
// ❌ 동기 — 응답 올 때까지 이 스레드는 아무것도 못 한다
var result = client.Connect();

// ✅ 비동기 — 기다리는 동안 스레드를 놓아준다
var result = await client.ConnectAsync();
```

| 용어 | 뜻 |
|---|---|
| **`Task`** | "나중에 끝날 작업". 결과가 있으면 `Task<T>` |
| **`async`** | 이 함수 안에서 `await` 를 쓰겠다는 표시 |
| **`await`** | "이 작업이 끝날 때까지 여기서 양보하고 기다린다" |

> 📖 **비유**: 식당에서 주문하고 **서서 기다리는 것**(동기)과
> 진동벨 받고 **자리에 앉는 것**(비동기)의 차이다.
> 비동기는 기다리는 동안 그 사람(스레드)이 다른 일을 할 수 있다.

### `ConfigureAwait(false)`

```csharp
await SomethingAsync().ConfigureAwait(false);
```

"이 작업이 끝난 뒤 **원래 있던 곳으로 돌아가지 않아도 된다**"는 표시다.

📌 안 쓰면 백그라운드 작업이 끝날 때마다 UI 스레드로 되돌아온다.
수집 루프가 UI 스레드에서 돌면 **화면이 그만큼 멈춘다.**

### 취소 토큰 (CancellationToken)

```csharp
await client.ConnectAsync(options, ct);
```

"이 작업을 중간에 그만둘 수 있게 하는 손잡이"다.
앱이 종료될 때 이 토큰을 당기면 모든 대기가 정리된다.

**타임아웃**에도 쓴다 — `new CancellationTokenSource(TimeSpan.FromSeconds(20))`
는 20초 뒤 자동으로 취소한다.

### 이벤트 핸들러 (`+=`)

```csharp
client.ApplicationMessageReceivedAsync += e => { …메시지 처리… };
```

"메시지가 오면 이 코드를 실행해 달라"고 등록하는 것.
우리가 부르는 게 아니라 **라이브러리가 우리를 부른다**(콜백).

### fire-and-forget (`_ =`)

```csharp
_ = InvokePingAsync(body);   // 기다리지 않는다
```

**의도적으로 기다리지 않는다**는 표시다.

📌 핑 한 번에 최대 1,000개의 응답을 발행할 수 있는데,
그걸 수신 핸들러 안에서 기다리면 **그동안 MQTT 수신이 통째로 멈춘다.**

> 🔒 대신 **그 안에서 예외를 반드시 흡수**해야 한다.
> 아무도 안 보는 작업의 예외는 프로세스를 죽일 수 있다.

### 스레드 안전 도구

| 도구 | 하는 일 |
|---|---|
| **`lock`** | 한 번에 한 스레드만 들어가게 |
| **`Interlocked.Increment`** | 락 없이 안전하게 +1 |
| **`Interlocked.Read`** | 락 없이 안전하게 읽기 |
| **`Volatile.Read`** | 캐시된 옛 값이 아니라 **진짜 현재 값**을 읽기 |

📌 초당 수만 건이 지나가는 경로에서 `lock` 을 걸면 **그 자체가 병목**이 된다.
단순 카운터에는 `Interlocked` 가 훨씬 싸다.

## 6. 연결의 생명주기 — 여기가 이 층의 핵심

```
   [연결 시도] ──성공──▶ [연결됨] ──▶ [구독] ──▶ [메시지 수신]
        │                    │
        │ 실패                │ 끊김 (절전 · 브로커 종료 · 네트워크)
        ▼                    ▼
   [재시도 루프] ◀────────────┘
        │
        └──▶ 붙으면 다시 [구독]  ← 🔑 이걸 빼먹으면 "연결은 됐는데 데이터가 안 온다"
```

### ⭐ 가장 비쌌던 사고

```csharp
while (!ct.IsCancellationRequested && !client.IsConnected)
{
    try { await Task.Delay(delay, ct); await client.ConnectAsync(options, ct); }
    catch { /* 계속 재시도 */ }
}
```

**이 `while` 이 `if` 면 시스템이 영구 정지한다.**

> 끊김 이벤트는 **"연결됐던 세션이 끊길 때"만** 발생한다.
> 한 번만 시도하고 실패를 삼키면, 클라이언트는 (재)연결된 적이 없으므로
> **그 이벤트가 다시 발생하지 않는다.**
>
> 절전 7시간 복귀 후 수집·대시보드가 정지했고, 팜만 살아 있어
> "발행은 되는데 아무도 수신 못 함" 상태가 됐다.
> 화면은 멀쩡해 보여서 **"네트워크 문제"로 오진하기 딱 좋았다.**

### 첫 연결 실패도 같은 함정이다

명세는 "끊긴 뒤"만 다루는데, **한 번도 연결된 적이 없으면** 그 이벤트가 아예 안 온다.
기동 순서를 지키면 안 생기지만 — **순서에 의존하는 시스템은 언젠가 깨진다.**

→ 첫 연결 실패용 재시도 루프를 따로 뒀다.

### keepalive 5초

**keepalive** = "나 살아 있다"를 주기적으로 알리는 신호.
이 주기 안에 반응이 없으면 끊긴 것으로 본다.

| 값 | 문제 |
|---|---|
| 15초(기본) | 좀비 소켓 감지가 늦다 |
| 1~2초 | CPU 부하 시 **오탐 단절** |
| **5초** | 회복 속도와 안정성의 균형점 |

> **좀비 소켓** = 실제로는 죽었는데 `IsConnected` 가 `true` 를 돌려주는 상태.
> TCP 는 양쪽 + 네트워크 카드가 모두 살아 있어야 유지되는데, 절전 중 그게 깨진다.

### 클라이언트 ID 는 고정

```csharp
.WithClientId("ingest-main")
.WithCleanSession(false)      // 브로커가 QoS1 큐를 보존
```

📌 둘은 **짝**이다. 브로커가 단절 중 메시지를 **그 클라이언트 앞으로** 큐잉했다가 재전달한다.
ID 가 랜덤이면 재연결할 때마다 **다른 클라이언트**가 되어 그 큐가 통째로 버려진다.

## 7. 센서 팜 — 악조건을 의도적으로 만든다

### 이 앱이 왜 납품물인가

실제 센서 없이 이 시스템의 신뢰성을 **증명하는 유일한 수단**이다.

| 조작 | 재현하는 것 |
|---|---|
| 오프라인 토글 | 센서가 죽음 → 복구 시 백필 |
| 이상치 주입 | 센서 글리치 → I7 격리 |
| 발행 속도 다이얼 | 폭주 → 백프레셔 · 과부하 폐기 |
| "현실 모드"(분당 1건) | 배치형 센서 → 적응 임계 |

### 엔진은 MQTT 를 모른다

```
SensorFarmEngine   "무엇을 발행할지" 계산만        ← 브로커 없이 검증
      ↓
호출 측            실제 발행
```

링버퍼·폐기 계수·백필·응답 대상 선정은 전부 **순수 로직**이다.
발행과 얽어 두면 "유실을 제대로 세는가" 같은 핵심 검사가
통합 테스트에 묶여 느리고 불안정해진다.

### 링버퍼 — 오프라인 동안 쌓아 두기

**링버퍼(ring buffer)** = 크기가 정해진 버퍼. 가득 차면 가장 오래된 것을 밀어낸다.

```
   센서 오프라인
       ↓
   [■■■■■■□□□□]  최대 600건 (초당 1건 = 약 10분치)
       ↓
   600 초과 → 오래된 것부터 버림 + 카운터 +1
       ↓
   복구 → 원본 시각 그대로 백필
```

| 단절 길이 | 결과 |
|---|---|
| **≤ 약 10분** | **무손실** — 복구 시 전부 백필, 중복은 수신 측이 접는다 |
| **> 약 10분** | 초과분 폐기 — **유실 건수가 화면에 표시됨** |

> 🔑 무한 버퍼는 불가능하므로 **폐기는 설계상 한계이지 결함이 아니다.**
> 결함이었던 것은 한계가 아니라 **한계를 감춘 것**이다 —
> 화면이 「유실 0」을 하드코딩된 문자열로 띄우고 있어서,
> 실제로 폐기가 일어나는데도 무손실이라고 말했다.

### 백필은 원본 시각 그대로

📌 지금 시각으로 바꾸면 **"10분 전 손님"이 "방금 온 손님"**이 되어
시간대별 통계가 통째로 어긋난다.

중복은 수신 측 멱등 판정이 접으므로 겹쳐 보내도 두 번 세어지지 않는다.

### 죽은 센서는 응답하지 않는다

📌 죽은 센서가 생존 응답을 보내면 **관제실이 그 센서를 영원히 못 찾는다.**

## 8. 명부 — I5 의 분모가 나오는 곳

```
본사 1 → 본부 2(수도권·영남) → 매장 12 → 센서 1,000
```

**센서 ID 는 결정적**이어야 한다 — 같은 입력이면 항상 같은 ID.

> 난수나 시각이 섞이면 재시작할 때마다 **"새 센서 1,000대"**가 나타나고,
> **옛 센서 1,000대는 영원히 오프라인**으로 남는다.

### 이것이 왜 "분모"인가

```
❌ 가동률 = 온라인 수 / 지금까지 본 센서 수
✅ 가동률 = 온라인 수 / 있어야 할 센서 수   ← 명부에서 나온다
```

📌 분모를 관측 기반으로 뒀다가:
**1,000대 중 50대가 무응답인데 화면은 950/950 = 100%** 를 띄웠다.
처음부터 죽어 있던 센서가 분모에서 통째로 빠졌기 때문이다.

**처음부터 없는 것은 영원히 안 보인다** — 가장 찾기 어려운 부류다.

## 9. 통합 테스트 — 단위 테스트와 뭐가 다른가

| | 단위 테스트 | 통합 테스트 |
|---|---|---|
| 대상 | 함수 하나 · 클래스 하나 | **여러 조각이 실제로 맞물리는지** |
| 외부 의존 | 없음 | 브로커 · 네트워크 · 파일 |
| 속도 | 밀리초 | 초 |
| 안정성 | 항상 같은 결과 | 타이밍에 따라 흔들릴 수 있음 |

### 왜 둘 다 필요한가

**단위 테스트가 전부 통과해도 실제로는 안 돌 수 있다.**

```
✓ 토픽 파싱 함수는 완벽하다
✓ 코덱도 완벽하다
✓ 파이프라인도 완벽하다
✗ 그런데 TLS 핸드셰이크가 안 돼서 아무것도 안 온다
```

그래서 이 층에는 **실제로 브로커를 띄우는 검증**이 붙는다.

### 흔들리지 않게 쓰는 법

```csharp
// ❌ 고정 시간만큼 자고 확인 — 빠른 기계에선 낭비, 느린 기계에선 실패
await Task.Delay(1000);
Assert.True(source.IsConnected);

// ✅ 될 때까지 짧게 자며 확인
await WaitUntilAsync(() => source.IsConnected, TimeSpan.FromSeconds(10));
```

그리고 **포트를 고정하지 않는다** — 테스트가 병렬로 돌면 반드시 부딪힌다.
빈 포트를 그때그때 얻어 쓴다.

 │         │                                              │

## 11. 용어 한눈에

| 용어 | 한 줄 |
|---|---|
| **브로커** | 메시지를 받아 토픽별로 분류·전달하는 중개자 |
| **발행 / 구독** | 보내기 / "이 토픽 오는 걸 나한테 달라" |
| **토픽** | 메시지의 주소. 슬래시로 계층을 만든다 |
| **페이로드** | 메시지 본문 |
| **와일드카드** | `#` — 그 아래 전부 |
| **QoS** | 배달 보장 수준 (0 던지고 잊기 / 1 재전송 / 2 정확히 1회) |
| **retain** | 마지막 값을 브로커가 붙잡고 있다 새 구독자에게 주는 기능 (**우리는 안 씀**) |
| **clean session** | `false` 면 브로커가 단절 중 메시지를 큐잉해 뒀다 재전달 |
| **keepalive** | "나 살아 있다" 주기 신호 |
| **좀비 소켓** | 실제로는 죽었는데 연결됐다고 보고하는 상태 |
| **루프백** | `127.0.0.1` — 이 컴퓨터 자신. 바깥에서 접속 불가 |
| **TLS** | 전송 암호화 (`https` 의 `s`) |
| **인증서** | "이 서버가 진짜다"를 증명하는 신분증 |
| **자체서명** | 내가 나에게 발급한 인증서. 제3자 검증 불가 |
| **CA** | 인증서를 보증하는 신뢰 기관 |
| **SAN** | 인증서가 유효한 이름·주소 목록 |
| **핸드셰이크** | TLS 연결을 여는 초기 절차 |
| **`async` / `await`** | 기다리는 동안 스레드를 놓아주는 방식 |
| **`Task`** | "나중에 끝날 작업" |
| **`CancellationToken`** | 작업을 중간에 그만두게 하는 손잡이 |
| **`ConfigureAwait(false)`** | 끝난 뒤 원래 스레드로 안 돌아와도 된다는 표시 |
| **fire-and-forget** | 의도적으로 기다리지 않고 던지기 (`_ =`) |
| **콜백 / 이벤트 핸들러** | 라이브러리가 우리를 부르는 방식 (`+=`) |
| **`Interlocked`** | 락 없이 안전하게 세기 |
| **`Volatile.Read`** | 캐시된 옛 값이 아니라 진짜 현재 값 읽기 |
| **링버퍼** | 크기가 정해진 버퍼. 차면 오래된 것부터 밀어낸다 |
| **백필** | 못 보낸 것을 복구 후 몰아 보내기 |
| **멱등** | 여러 번 해도 한 번 한 것과 같음 |
| **느슨한 결합** | 서로를 직접 모르고 메시지로만 이어짐 |
| **통합 테스트** | 여러 조각이 실제로 맞물리는지 확인 |

## 12. 이 층이 지키는 약속 다섯

| 약속 | 어떻게 |
|---|---|
| **설치 없이 돈다** | 브로커가 앱 안에 있다. exe 만 실행하면 된다 |
| **평문으로는 못 붙는다** | TLS 를 켜면 평문 엔드포인트를 제거한다 |
| **끊겨도 반드시 돌아온다** | 연결될 때까지 무한 재시도 · 재구독까지 복원 |
| **10분까지는 무손실** | 링버퍼 600건 · 원본 시각 백필 · 중복은 수신 측이 접는다 |
| **버린 건 반드시 센다** | 그 이상은 폐기하되 **건수를 화면에 드러낸다** |

> 🧭 다섯 번째가 핵심이다.
> **한계가 있는 것은 결함이 아니다. 한계를 감추는 것이 결함이다.**

# 화면 층 상세 — 직접 그리는 이유와, 그러다 화면을 얼린 이야기

> 5층에서 만든 것을 정리한다.
> 앞의 네 층이 「사실을 지키는」 일이었다면, 이 층은 **「그 사실을 사람에게 보여주는」** 일이다.
>
> 그리고 이 층에서 가장 많이 배운 것은 그리는 기술이 아니라
> **「효율적이다」라고 말하려면 무엇이 성립해야 하는가**였다.

## 0. 이 층이 정확히 무엇인가

| # | 무엇 | 대답하는 질문 |
|---|---|---|
| ① **렌더 정책** | 언제 얼마나 자주 그릴 것인가 | 부하가 없을 때도 **CPU 를 써야 하는가** |
| ② **공유층(Ui.Common)** | 창 크롬 · 배경 · 패널 · 활력 표시등 | 세 앱이 같은 모양이려면 무엇을 공유하나 |
| ③ **앱 3개** | 관제실 · 센서 팜 · 상황판 | 각자 무엇을 보여주고 무엇을 조작하나 |
| ④ **기동 스모크** | 앱이 실제로 뜨는가 | `dotnet test` 가 **못 보는 것**은 무엇인가 |

## 1. WPF 기초 용어

| 용어 | 뜻 |
|---|---|
| **WPF** | Windows 데스크톱 UI 프레임워크 |
| **XAML** | 화면 구조를 적는 마크업(HTML 같은 것) |
| **코드비하인드** | 그 XAML 에 딸린 C# 파일(`MainWindow.xaml.cs`) |
| **`FrameworkElement`** | 화면 요소의 기본 타입. 상속해서 **직접 그릴** 수 있다 |
| **`OnRender`** | "이제 그려라"라고 WPF 가 부르는 함수 |
| **`DrawingContext`** | 그리기 명령을 받는 도구(선·사각형·텍스트) |
| **UI 스레드** | 화면을 다루는 유일한 스레드. **여기가 막히면 화면이 굳는다** |
| **디스패처** | UI 스레드에 할 일을 줄 세우는 장치 |
| **`DispatcherTimer`** | UI 스레드에서 주기적으로 실행되는 타이머 |

### 레이아웃 컨테이너

| 이름 | 하는 일 |
|---|---|
| `Grid` | 행·열로 나눈다 |
| `StackPanel` | 한 줄로 쌓는다 — ⚠️ **넘치면 말없이 자른다** |
| `WrapPanel` | 한 줄로 쌓되 **넘치면 다음 줄로** 넘긴다 |
| `UniformGrid` | 균등하게 나눈다 |
| `Viewbox` | 안쪽 내용을 **비율대로 늘리거나 줄인다** |

## 2. 왜 차트 라이브러리를 쓰지 않나

이 프로젝트는 그래프·표·게이지를 **전부 직접 그린다.** LiveCharts·OxyPlot 같은 것을 안 쓴다.

### 이유 — 그리는 빈도를 우리가 통제해야 하기 때문

📌 실측:

> 부하가 **15 msg/s 뿐인데 세 앱이 CPU 314%** 를 쓰고 있었다.
> 원인은 데이터가 아니라 **그리기**였다 —
> 세 앱 모두 33ms 마다 화면 전체를 다시 그렸고, 그건 **부하와 무관하게 항상** 일어났다.

라이브러리는 "부하가 없을 때 CPU 도 안 쓴다"를 **보장해 주지 않는다.**
우리는 그걸 **주장해야** 하므로, 그리는 시점을 손에 쥐어야 한다.

> 🔑 이건 성능 문제이자 **주장의 문제**다.
> **「이 시스템은 효율적이다」라고 말하려면 부하가 없을 때 CPU 도 내려가야 한다.**

### 대가

직접 그리면 자유롭지만 **잘못하면 UI 를 통째로 얼린다.** §4 가 그 이야기다.

## 3. 프레임 정책 — 상황에 따라 다르게 그린다

```
보고 있고 값도 움직임   →  33ms   (30fps)  부드러움이 값을 하는 유일한 구간
보고는 있지만 조용함    →  125ms  (8fps)   시계·초당 값에는 충분
창이 뒤에 있음          →  500ms  (2fps)   아무도 안 보는 화면에 CPU 를 쓰지 않는다
애니메이션 끔           →  1000ms (1fps)   ⚠ 완전히 세우지는 않는다
```

### 🔑 애니메이션을 꺼도 완전히 멈추지 않는 이유

세우면 **창 크기 변경·데이터 갱신 후 다시 그릴 사람이 없어** 화면이 낡은 채로 남는다.
아주 낮은 빈도로 **유지만** 한다.

### 이 판정이 Core 에 있다

```
Core/Rendering/FramePolicy.cs
```

이상해 보이지만 — 여기 있는 것은 **그리는 코드가 아니라 「언제 그릴지 판정하는 규칙」**이다.
판정이므로 순수해야 하고, 순수하므로 **화면 없이 검증**된다.

## 4. ⭐ 텍스트 캐시 — 화면이 굳던 사고

### 증상

> 관제실·대시보드의 **시계·숫자·활력점이 한 시점에 굳었다.**
> **애니메이션은 계속 돌았다.**
> 백엔드는 정상이었다 — DB 는 계속 커지고 브로커 연결도 유지됐다.
>
> → 겉보기엔 **「연결 끊김」**으로 보였다.

### 원인 — 둘이 겹쳤다

**① 임베드 폰트 재로딩**

앱 폰트가 프로젝트에 **임베드**되어 있으면,
`FormattedText`(그릴 텍스트 객체)를 새로 만들 때마다 WPF 가 **폰트 스트림을 다시 연다.**

패널들이 33ms 마다 수백 개를 만들면 **UI 스레드가 포화**된다.

**② 우선순위 역전**

```
애니메이션 틱  →  Render 우선순위 (높음)
데이터 틱      →  기본값(Background, 낮음)
```

렌더가 무거워지면 데이터 틱이 **영원히 순번을 못 받는다.**

### 왜 진단이 어려웠나

```
백엔드는 다른 스레드   →  멀쩡히 계속 돈다
화면만 굳음            →  DB 는 계속 커진다
겉보기엔 연결 끊김     →  엉뚱한 곳(재연결)을 판다
```

**실제 진단 근거**: 스택 샘플 **5/5 가 폰트 스트림을 여는 함수 안**이었다.

> 🧭 **「멈췄다」일 때 연결부터 의심하면 시간을 버린다.**
> 순서를 고정한다: ① 백엔드가 정말 죽었나 → ② 소켓 → ③ **UI 스레드가 어디 있나** → ④ 화면 비교

### 봉합

```csharp
// ❌ 매번 새로 만든다 — 폰트 스트림을 매번 연다
var text = new FormattedText(…);

// ✅ 같은 문자열·서체·크기·색이면 같은 인스턴스를 돌려받는다
var text = FormattedTextCache.Get(…);
```

**재사용이 안전한 이유**: 그리는 **위치는 그리기 명령의 인자**다.
반환된 객체를 보관하거나 변형하지 않는 한(폭·높이 읽기는 무해) 여러 번 그려도 된다.

그리고 **데이터 틱의 우선순위를 올린다.**

```csharp
new DispatcherTimer(DispatcherPriority.DataBind)   // 명시한다
```

> 🔒 **굶어야 할 쪽은 장식이다.** 숫자가 아니라.

## 5. 시각 설계 — 형태로 위계를 만든다

### 🔑 선 위계 4단계

**화면이 밋밋해 보이는 원인은 대개 색이 아니라 「선이 한 단계뿐」이라는 데 있다.**

패널 경계·구분선·눈금이 전부 같은 밝기면, 눈이
**「무엇이 큰 덩어리이고 무엇이 그 안의 칸인지」**를 형태로 알 수 없어 화면이 **한 겹**으로 읽힌다.

| 단계 | 두께 | 용도 |
|---|---|---|
| **Faint** | 1 | 배경 격자 — **있는 줄 모르지만 없으면 바닥이 빈다** |
| **Soft** | 1 | 패널 **안쪽 칸** 나눔 |
| **Base** | 1 | **패널 경계** |
| **Strong** | 1.2 | 코너 브래킷 — **시선을 붙잡는 유일한 단계** |

> 🔒 **용도**로 나눈 것이지 취향이 아니다. 임의로 합치지 말 것.

### 배경 3층

```
① 바닥        단색
② 격자        44px 간격 · 5칸마다 굵게
③ 십자 표식   굵은 선이 만나는 지점
④ 비네트      가장자리만 살짝 어둡게
```

> 🔴 **넷 다 알파가 매우 낮다. 눈에 띄면 실패다** —
> 배경은 **인지되지 않으면서 깊이만** 만들어야 한다.
>
> 십자 표식은 제도판·레이더의 기준점이다.
> 격자가 「무늬」가 아니라 **「눈금」으로 읽히게** 하는 최소 장치이고,
> **요소를 늘리지 않고 정밀함만 올리는** 몇 안 되는 수단이다.

### 패널이 「떠 있게」 만드는 법

```
Panel 색을 Void 보다 **약간만** 밝게 한다
```

🔑 크게 벌리면 카드가 「떠 보이는」 게 아니라 **「붕 뜬다」**.
그리고 배경 위에 알파가 낮은 채움색을 쓰면 **뒤가 비쳐** 진짜로 떠 있는 느낌이 난다.

### `Freeze` — 얼린다

```csharp
brush.Freeze();
```

WPF 의 그리기 객체는 **얼릴 수 있다** — "이제 안 바꾼다"는 선언이다.
얼리면 WPF 가 최적화하고, 여러 스레드에서 공유해도 안전하다.

🔒 고빈도 렌더 경로에서 **매 프레임 새로 만들면 할당이 쌓인다.**

## 6. 레이아웃 규칙 넷 — 전부 실제 사고에서 나왔다

### ① 가로 `StackPanel` 대신 `WrapPanel`

📌 가로 `StackPanel` 은 폭이 모자라면 넘친 자식을 **말없이 클립**한다.
**빌드·런타임 경고 0.** 헤더에 버튼을 하나 더 넣었더니 우측 버튼이 조용히 사라졌다.

> 🔑 **안 보이면 못 누르고, 못 누르면 없는 기능이다.**

### ② 값이 바뀌는 문구는 레이아웃을 흔들지 않는 곳에

📌 `과부하 폐기 232,347건` 처럼 길이가 변하는 칩을 헤더에 두면
**줄이 접혔다 펴져 화면 전체가 위아래로 출렁인다.**

→ 고정 위치에 두거나 `MinWidth` 를 준다.

### ③ 고정폭 대신 `Viewbox StretchDirection="DownOnly"`

📌 고정폭이면 폭이 모자랄 때 **줄지 않고 잘린다.**
`Viewbox` 로 감싸면 **작아질지언정 사라지지 않는다.**

### ④ 도구는 캡션 바에, 주인공은 헤더에

📌 도구를 헤더에 두면 **폭 경쟁에 끼어들어 가운데 KPI 를 잘라먹는다.**

## 7. 창 크롬 — 직접 만든 타이틀바

```xml
<Window WindowStyle="None"           <!-- 기본 타이틀바를 없앤다 -->
        AllowsTransparency="False">  <!-- 🔴 반드시 False -->
  <shell:WindowChrome.WindowChrome>
    <shell:WindowChrome CaptionHeight="36" CornerRadius="8" .../>
  </shell:WindowChrome.WindowChrome>
```

**`WindowChrome`** = 창 테두리·크기 조절·최대화 동작은 유지하면서 **모양만 우리가 그리게** 해 주는 장치.

### 🔴 `AllowsTransparency="False"` 를 지켜야 하는 이유

투명 창을 켜면 **ClearType 서브픽셀 렌더링이 꺼진다.**

> **ClearType** = 글자 가장자리를 픽셀의 R·G·B 소자 단위로 다듬어 또렷하게 만드는 기술.

영문은 티가 덜 나지만 **한글은 눈에 띄게 뭉개진다.**
같은 이유로 팝업도 투명하게 만들지 않는다.

## 8. 화면의 정직성 — 이 층의 진짜 규칙

### 🔒 상태 표시는 매 틱 재검증한다

```csharp
// ❌ 기동할 때 한 번 켜고 끝
BrokerDot.Fill = Ok;

// ✅ 매 틱 다시 묻는다
BrokerDot.Fill = _host.BrokerRunning ? Ok : Bad;
```

📌 한 번만 켜 두면 **수집 루프가 조용히 끝나도 초록으로 남는다.**

### 감사할 때 볼 네 가지 — 이 프로젝트의 오류는 전부 이 넷 중 하나였다

| # | 무엇 | 예 |
|---|---|---|
| ① | **하드코딩된 안심 문구** | 조건 없이 그려지는 `(유실 0)` · `● LIVE` |
| ② | **1회성 주장** | 기동 시 한 번 켜고 다시 확인 안 하는 상태 칩 |
| ③ | **분모** ⚠ | 비율의 분모가 「있어야 할 것」인가 「이미 본 것」인가 |
| ④ | **삼켜진 예외** | 실패했는데 화면은 직전 값이나 빈 값을 **최신인 척** 보여줌 |

### 이번에 화면에 박은 것들

```
✓ 브로커 칩 매 틱 재검증
✓ 과부하 폐기를 이상치보다 먼저    (데이터가 사라진 것이 더 심각)
✓ 「유실 0」은 반증 카운터가 있을 때만
✓ Demo 모드를 반드시 표시          (가짜를 실제인 것처럼 그리지 않는다)
✓ 온라인은 N / M                   (M 은 있어야 할 명부 기준)
✓ 매장은 목록에서 사라지지 않는다   (사라지면 "그런 매장이 없구나"가 된다)
✓ 「(전체 기간)」/「(이번 세션)」을 라벨에 명시
```

### 🔑 마지막 것이 의외로 중요하다

📌 센서 팜의 「누적 발신」은 **이번 세션만** 세고, 관제실의 「누적 수신」은 **전체 기간**이다.
둘 다 정확한데 나란히 놓으면 값이 크게 달라 보인다.

실제로 **24배 차이**가 나서 **「데이터가 유실됐다」로 읽힌** 적이 있다.

> **계산 오류보다 이런 의미 불일치가 숫자 신뢰를 더 크게 깨뜨린다.**

## 9. 자동화가 읽을 수 있게 남긴 것

### 커스텀 렌더 요소는 자동화에 안 보인다

**UI Automation(UIA)** = 화면 요소를 프로그램이 읽을 수 있게 하는 Windows 기능.
스크린 리더와 자동 테스트가 이걸 쓴다.

`OnRender` 로 직접 그린 것은 **그림일 뿐**이라 UIA 트리에 안 나타난다.

→ 그래서 **자동화가 읽어야 하는 문구**는 일부러 일반 텍스트 요소로 남긴다.

```xml
<TextBlock x:Name="HealthText"
           AutomationProperties.AutomationId="HealthText" … />
```

> 🔒 이 둘을 커스텀 렌더로 옮기면 **UIA 노드가 사라져 검증 게이트가 죽는다.**

### 조작 컨트롤 이름은 ASCII 로

```xml
<!-- ❌ 이름이 없으면 자동화가 한글 문구로 찾게 되고, 문구를 다듬는 순간 조용히 깨진다 -->
<Button Content="폭주 (5,000)" .../>

<!-- ✅ -->
<Button x:Name="PresetSurgeBtn" Content="폭주 (5,000)" .../>
```

`x:Name` 이 곧 자동화 식별자다.

## 10. 기동 스모크 — 테스트가 못 보는 것

### 왜 따로 필요한가

```
dotnet test  →  Core · Mqtt · Sqlite 만 본다 (테스트가 UI 앱을 참조하지 않는다)
                ↓
XAML 파싱 오류 · 리소스 누락 · App.xaml 결선  →  전부 그린인데도 남는다
```

📌 실제로 `App.xaml` 에 `x:Class` 가 빠져 **`App` 클래스가 통째로 죽어 있던** 적이 있고,
그때 **테스트는 전부 그린**이었다.

### 무엇을 보나

```
① 세 앱이 뜨는가
② 8초 뒤에도 살아 있는가
③ 창을 띄웠는가 (창 핸들이 있는가)
```

> 🔑 이 스크립트는 **「죽지 않는가」만** 본다.
> 「정상 동작」 판정은 `dotnet test` 와 손 확인의 몫이다 — **할 수 있는 것만 주장한다.**

### 🔴 TFM 폴더를 하드코딩하지 않는다

📌 실제로 3시간을 태운 함정:

```
bin\Debug\net8.0-windows\                 ← 8일 묵은 옛 잔재
bin\Debug\net8.0-windows10.0.19041.0\     ← 현재 빌드 산출물
```

검증 스크립트가 **8일 묵은 쪽**을 집었고, 그 옛 바이너리가 **고치기 전 동작**을 띄웠다.
**「수정이 안 먹었다」로 오해하기 딱 좋았다.**

→ 최신 빌드본을 찾아 실행하고, **어떤 바이너리를 띄웠는지 경로와 빌드 시각을 출력**한다.

### 🔴 그리고 이번에 하나 더 밟았다

스크립트가 **구문 오류로 실패**했다.
Windows PowerShell 5.1 이 **BOM 없는 UTF-8 을 ANSI 로 읽어서** 한글 주석의 따옴표가 깨졌다.

> **「코드가 맞는데 실행이 안 되는」 부류**다.
> 스크립트는 **반드시 한 번 돌려 봐야** 드러난다.

## 11. 용어 한눈에

| 용어 | 한 줄 |
|---|---|
| **WPF / XAML** | Windows 데스크톱 UI 프레임워크 / 화면 구조 마크업 |
| **코드비하인드** | XAML 에 딸린 C# 파일 |
| **`FrameworkElement`** | 화면 요소의 기본 타입. 상속하면 직접 그릴 수 있다 |
| **`OnRender`** | "이제 그려라"라고 WPF 가 부르는 함수 |
| **`DrawingContext`** | 그리기 명령을 받는 도구 |
| **UI 스레드** | 화면을 다루는 유일한 스레드. 막히면 화면이 굳는다 |
| **디스패처** | UI 스레드에 할 일을 줄 세우는 장치 |
| **`DispatcherPriority`** | 그 줄에서의 새치기 순위 |
| **우선순위 역전** | 덜 중요한 일이 더 중요한 일을 밀어내는 상태 |
| **`Freeze`** | 그리기 객체를 "이제 안 바꾼다"고 선언 — 최적화 + 스레드 안전 |
| **`FormattedText`** | 그릴 텍스트를 미리 배치·계산해 둔 객체 |
| **pixels per dip** | 화면 배율. 다르면 글자 모양도 달라진다 |
| **ClearType** | 글자를 픽셀 소자 단위로 다듬어 또렷하게 하는 기술 |
| **`WindowChrome`** | 창 동작은 유지하고 모양만 직접 그리게 해 주는 장치 |
| **히트 테스트** | 이 좌표에 어떤 요소가 있는지 찾는 것 |
| **UI Automation(UIA)** | 화면 요소를 프로그램이 읽을 수 있게 하는 Windows 기능 |
| **`AutomationId`** | 자동화가 요소를 찾는 이름 |
| **`Viewbox`** | 안쪽 내용을 비율대로 늘리거나 줄이는 컨테이너 |
| **`WrapPanel`** | 넘치면 다음 줄로 넘기는 컨테이너 |
| **TFM** | 대상 프레임워크 이름(`net8.0-windows10.0.19041.0`) |
| **기동 스모크** | 앱이 뜨고 살아 있고 창을 띄웠는지만 보는 최소 검사 |

## 12. 이 층이 지키는 약속 다섯

| 약속 | 어떻게 |
|---|---|
| **부하가 없으면 CPU 도 내려간다** | 상황별 프레임 정책 · 창이 뒤면 더 낮게 |
| **화면은 어떤 부하에서도 안 굳는다** | 텍스트 캐시 · 워커 우선순위 낮춤 · 데이터 틱 승격 |
| **안 보이는 것은 없는 기능이다** | `WrapPanel` · `Viewbox` · 도구는 캡션 바에 |
| **상태 표시는 매번 다시 묻는다** | 조건 없이 그려지는 안심 표시를 만들지 않는다 |
| **못 본 것을 봤다고 하지 않는다** | Demo 모드 표시 · N/M 표기 · 매장이 사라지지 않음 |

## 부록 · 다섯 층을 한 장으로

| 층 | 한 줄 | 새로 배운 것 |
|---|---|---|
| **1층 Core** | 규칙을 순수 함수로 못박는다 | 불변식 · 멱등키 · 계약으로 강제하기 |
| **2층 Sqlite** | 파일에 안전히 담고 늙은 건 접는다 | 트랜잭션 · WAL · 롤업 · 인덱스 트레이드오프 |
| **3층 Mqtt** | 프로그램끼리 느슨하게 잇는다 | pub-sub · QoS · TLS · 비동기 · 재연결 |
| **4층 판정** | 무엇이 사실인지 정한다 | **분모** · fail-closed · 「모름」을 값으로 |
| **5층 WPF** | 그 사실을 사람에게 보여준다 | 커스텀 렌더 · 프레임 정책 · 화면의 정직성 |

### 다섯 층을 관통하는 한 문장

> ## 🧭 모르는 것을 아는 것처럼 그리지 마라.

- **1층** — 중복은 접고, 불가능한 값은 격리해서 **센다**
- **2층** — 총계는 변하지 않고, 저장한 것은 그대로 돌아온다
- **3층** — 버린 것은 반드시 세고, 한계를 감추지 않는다
- **4층** — 침묵은 0이 아니고, 못 본 것은 100%가 아니다
- **5층** — 안심 문구는 **반증할 카운터가 있을 때만** 쓴다

> 이 시스템의 결함은 전부 「안 돌아감」이 아니라 **「돌아가는데 조용히 틀림」**이었다.
> 그래서 설계의 목표가 **정확성**이 아니라 **틀렸을 때의 가시성**이 된다.

# 용량과 확장 — "센서 몇 대까지 되나요?"

> 이 질문의 답은 **대수가 아니라 초당 이벤트 수**다.
> 이 문서는 그 이유와, 한계에 부딪혔을 때 무엇부터 손대는지를 정리한다.

---

## 1. 먼저 — 헷갈리기 쉬운 세 가지

### ① 프리셋 숫자는 **센서 개수가 아니다**

센서는 **항상 1,000대**다. 프리셋 숫자는 **초당 몇 번 보고하느냐**다.

| 프리셋 | 초당 관측 | 센서 하나의 보고 주기 |
|---|---|---|
| 현실 (분당 1건) | 17 | **1분**에 한 번 ← 실제 센서에 가장 가깝다 |
| 정상 (17/s) | 17 | 59초에 한 번 |
| 빠름 (500/s) | 500 | 2초에 한 번 |
| 폭주 (5,000/s) | 5,000 | 0.2초에 한 번 |
| 극한 (20,000/s) | 20,000 | **50ms**에 한 번 |

### ② 관측 1건 ≠ 사람 1명

```
관측 1건 = { sensorId, 시각, in: 5명, out: 3명 }
                                 ↑ 사람 수는 여기에 들어간다
```

한 건에 담을 수 있는 인원은 **최대 100명**(`DefaultMaxPlausibleCountPerReading`, I7).
그 이상은 「물리적으로 불가능」으로 격리한다.

> 🔑 **사람이 몰려도 관측 건수는 안 늘어난다.** `count` 값만 커진다.
> 5,000명이 몰리면 센서 1,000대가 각자 `in: 5` 를 보고하면 된다 — 관측은 1,000건 그대로다.

### ③ 「한 틱에 명부 한 바퀴」는 초당 상한이 아니다

```
틱 = 50ms  ·  1초 = 20틱
틱당 상한 = 명부 한 바퀴 (센서 1,000대)
        ↓
초당 상한 = 1,000 × 20 = 20,000 관측/s
```

극한 프리셋이 정확히 이 상한선이다.

## 2. 발행 모델 — 상한은 언제 걸리나

발행 루프는 50ms마다 돌면서 `목표 속도 × 실제 경과 시간` 만큼 관측을 만든다.
그리고 명부를 **커서로 순서대로** 돈다.

```
정상 (틱 50ms · 5,000/s 목표)
  필요 250건  →  커서 [0...249]      ← 명부의 0.25바퀴
  다음 틱      →  커서 [250...499]    ← 다른 센서, 다른 시각
                                       상한에 안 걸림 ✓

밀림 (틱 1.1초 · 20,000/s 목표)
  필요 22,000건 →  상한 1,000 으로 자름
  실제 발행 = 1,000 ÷ 1.1초 = 약 900/s
```

> 🔴 **왜 자르나**: 자르지 않으면 커서가 명부를 여러 바퀴 돌아
> **같은 센서가 같은 시각으로** 재발행된다. 멱등 키(`SensorId|밀리초|Direction`)가 겹쳐
> 수신 측이 **전부 중복으로 접는다** — 실제로 「수신은 되는데 저장이 0」을 만든 원인이다.
> 상세 → [신뢰성 기록 R-12](reliability-lessons.md)
>
> 🔑 물리적으로도 이게 맞다. 센서 1,000대가 한 순간에 각자 한 번 관측하는 것이 상한이고,
> **서버가 밀렸다고 센서가 과거를 더 보내주지는 않는다.**
> 잘린 몫은 버리되, 실측 발행량이 목표보다 낮게 나와 **정직한 신호**가 된다.

### ⚠️ 디버거를 붙이면 이 상한에 늘 걸린다

Visual Studio F5 로 띄우면 틱이 **50ms → 약 1.1초**(22배)까지 밀린다.
JIT 최적화가 꺼지고 스레드 전환 비용이 커지기 때문이다.

> **부하·성능 측정은 반드시 `실행.bat`(디버거 없이)** 으로 한다.
> 디버거 하의 숫자는 실제 성능이 아니다.

## 3. 실측 능력치

🔴 **지연은 단일 값이 아니다 — DB 크기에 딸린 값이다.**
아래를 두 시점에 나눠 적는 이유가 그것이다. 같은 부하인데 DB 가 2.9배 커지자 지연이 **3배 이상** 늘었다.

### DB 1.4GB 시점

| 항목 | 실측값 | 조건 |
|---|---|---|
| 저장 (관제실) | 약 17,000 이벤트/s | SQLite · 배치 커밋 · 워커 8 |
| 처리 지연 | **55~65µs** | 폭주(5,000/s) |

### DB 4.0GB 시점 (2026-08-07 재측정)

| 부하 프리셋 | 발행 실측 | 수신 | 워커 | 처리 지연 | 백로그 | 과부하 폐기 |
|---|---|---|---|---|---|---|
| 폭주 (5,000) | 4,929/s | 5,007 msg/s → 약 9,800 evt/s | **3** | **211.6µs** | **0** | 없음 |
| 극한 (20,000) | **16,838/s** | 16,765 msg/s | **8**(상한) | **408.6µs** | **149,745** | **122,018건** |

**읽는 법**

- **폭주까지는 여유다** — 백로그 0, 폐기 0. 워커도 3개면 충분해 상한까지 안 간다.
- **극한은 받아내지 못한다.** 발행 자체가 목표 20,000 에 못 미쳐 16,838/s 에서 막히고,
  그마저도 저장이 못 따라가 대기열이 상한 150,000 에 **149,745** 까지 찬다.
  넘친 **122,018건은 버리되 세어서 화면에 올린다.**
- 워커 상한 8 × `PerWorkerEventsPerSec` 2,500 = **20,000 evt/s** 가 처리 천장이다.
  극한은 메시지 16,765/s × 2(in·out) ≈ **33,000 evt/s** 를 요구하므로 천장을 넘는다.
  숫자가 어긋나는 게 아니라 **설계된 천장에 부딪힌 것**이다.

> ⚠️ **「센서 50만 대」 계산은 DB 1.4GB 의 저장 능력 17,000 evt/s 를 전제로 한다.**
> DB 가 커지면 그 값도 내려가므로, 규모를 말할 때는 **어느 시점의 DB 인지**를 함께 적어야 한다.

## 4. 그래서 센서 몇 대까지 되나

```
센서 N대  ×  보고 주기  =  초당 메시지  ×2  =  초당 이벤트
                                              ↓
                                    저장 능력 17,000 evt/s 와 비교
```

| 시나리오 | 초당 이벤트 | 판정 |
|---|---|---|
| 1,000대 · 1분 주기 | 33 | 여유 **500배** |
| 20,000대 · 1분 주기 | 666 | 여유 **25배** |
| **50만 대 · 1분 주기** | 약 17,000 | **한계선** |
| 20,000대 · **1초 주기** | 40,000 | ❌ 초과 |

> **분당 1회 보고 기준 — 지금 구조로 센서 약 50만 대까지 감당한다.**
>
> ⚠️ 단, 이건 **저장 능력만 놓고 계산한 값**이다.
> 실제로 그 규모를 주장하려면 브로커 연결 수·메모리·헬스 추적기(센서당 딕셔너리 항목)도
> 함께 재봐야 한다. **재보지 않은 것을 능력치로 말하지 않는다.**

## 5. 한계에 부딪히면 — 손대는 순서

### ① 먼저 어디서 막히는지 잰다

`17,000 evt/s` 는 실측이지만 **무엇이 병목인지는 아직 모른다.**
SQLite INSERT 인가, 디스크 쓰기인가, 직렬화인가.
**측정 없이 고치면 엉뚱한 데를 고친다.**

### ② 엣지에서 묶는다 (가장 효과적)

#### 「엣지(Edge)」란

**데이터가 생기는 현장 쪽**을 뜻한다. 센서 바로 옆에 있는 작은 컴퓨터
(게이트웨이 · 산업용 PC · 때로는 센서 자체)다.

```
        엣지 (현장)                      센터 (중앙)
┌──────────────────────┐          ┌──────────────┐
│  [매장 A]            │          │              │
│   센서 ─┐            │          │   관제실     │
│   센서 ─┼→ 게이트웨이 │──인터넷──→│   서버 + DB  │
│   센서 ─┘            │          │              │
└──────────────────────┘          └──────────────┘
         ↑ 여기가 엣지
```

#### 「엣지에서 묶는다」가 무슨 뜻인가

| | 방식 | 본사로 가는 연락 |
|---|---|---|
| 엣지 없음 | 손님 한 명마다 **본사에 전화** | 하루 5,000통 |
| **엣지 있음** | 매장에서 세어뒀다가 **1분에 한 번 보고** | 하루 480통 |

세는 건 똑같다. **어디서 세느냐**가 다를 뿐이다.

```
엣지 없음:  센서 → "1명" → 서버   (초당 수천 번)
엣지 있음:  센서 → [게이트웨이가 1분간 모음] → "60명" → 서버   (1분에 1번)
```

| 이점 | 설명 |
|---|---|
| 네트워크 부하 ↓ | 60건이 1건으로 — 회선비도 준다 |
| 서버 부하 ↓ | 저장할 행 수가 1/60 |
| 끊겨도 버팀 | 인터넷이 끊겨도 게이트웨이가 로컬에 쌓아둔다 |
| 응답이 빠름 | 급한 판단은 현장에서 즉시 |

> 🔑 **서버 코드를 한 줄도 안 고치고 부하를 1/60 로 줄인다.**
> 실제 IoT 시스템의 표준 해법이고, 확장이 필요할 때 **가장 먼저 손댈 곳**이다.
>
> 📌 지금 시스템에는 엣지가 없다(센서가 브로커로 직접 쏜다).
> 다만 `현실 (분당 1건)` 프리셋이 그 효과를 흉내 낸다 —
> 「센서가 자기 안에서 1분간 세뒀다가 한 번에 보낸다」고 가정한 것이고,
> 실제 매장용 유동인구 센서가 대부분 그렇게 동작한다.

### ③ 저장 계층 교체

SQLite 는 단일 파일 · 단일 writer 다. 그 이상이 필요하면:
- **시계열 DB**(TimescaleDB · InfluxDB) — 시간축 파티셔닝이 기본
- 또는 **사이트별 DB 분할**(샤딩)

### ④ 수집을 수평 분할

```
지금:  관제실 1개가 전 센서를 구독
개선:  MQTT 토픽으로 나눠 관제실 N개가 각자 일부만 구독
       (토픽이 이미 site/sensor 계층이라 나누기 쉽다)
```

## 6. 이미 준비돼 있는 것

확장을 아예 못 버티는 구조는 아니다.

| 장치 | 역할 |
|---|---|
| 배치 커밋 (`TryAppendBatch`) | 건별 트랜잭션 대비 **16배** |
| 적응 워커 (1~8) | 백로그에 따라 자동 증감 |
| 롤업 + 프룬 | 3시간 지난 원본을 집계로 접어 **DB 무한 성장 차단** |
| 바운드 큐 + 폐기 계수 | 넘치면 **버리되 센다** — 조용히 죽지 않는다 |
| 상한 + 실측 표시 | 못 따라가면 **목표 대비 실측**이 낮게 나와 드러난다 |

## 7. 아직 안 재본 것

정직하게 남긴다.

- **백필 폭주** — 오프라인이던 센서 수백 대가 동시 복구되면
  버퍼(센서당 600건)를 한꺼번에 쏟는다. 500대면 순간 30만 건.
  현장에서 충분히 일어난다(공유기 재부팅 · 회선 복구 · 정전 복구).
  타일을 여러 개 죽였다 한꺼번에 살리면 재현되지만 **아직 측정하지 않았다.**
- 브로커 동시 연결 수 한계
- 센서 수가 늘 때의 메모리 사용량(헬스 추적기 · 프로비저닝 명부)

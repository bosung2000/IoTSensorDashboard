# 화면 안내 — 무엇이 어디서 오고 어떻게 계산되나

> 각 화면의 **모든 표시 요소**를 하나씩 훑는다.
> 「이 숫자는 어디서 온 값인가 · 어떻게 계산되나 · 언제 갱신되나 · 이상하면 무슨 뜻인가」.

> ⚠️ **부분 갱신 필요** — 상황판과 관제실에 화면 요소가 크게 늘었다.
> 아래 §0-1 에 새 구성을 요약했고, **각 요소별 상세는 아직 이 문서에 반영되지 않았다.**
> 새로 생긴 지표를 읽는 법은 [화면 읽는 법](reading-the-screens.md) 에 정리돼 있다.

## 0-1. 지금의 화면 구성 (요약)

**종합 상황판** — 패널 10장

```
┌──────────────────────────────────────────────────────────────┐
│ KPI 5   누적유입 · 누적유출 · 현재체류 · 온라인센서 · 유일이벤트   │
├───────────┬──────────────────────────────┬───────────────────┤
│ 스파크라인 │ 매장 카드 스트립               │ 그룹 가동률(도넛)  │
│ (매장 추이)├──────────────────────────────┤                   │
│           │ 토폴로지 (본사·본부·매장 그래프) │ 처리량 Top 5      │
│ 유입 Top5 ├──────────────────────────────┤                   │
│           │ 분단위 추이 차트               │ 유출 Top 5        │
│           ├───────────────┬──────────────┤                   │
│           │ 매장별 상태표  │ 이벤트 로그   │                   │
└───────────┴───────────────┴──────────────┴───────────────────┘
```

**관제실** — 파이프라인 그림 + 감지 피드

```
센서 응답률 100.00%          데이터 수신율 20.40%      ← 두 비율을 나란히
     ┌─────┐   ┌────┐   ┌────────┐   ┌────────┐
센서 →│수집 큐│ → │저장 │ → │중복 접음│ → │대시보드 │   + 감지 피드(우측)
     └─────┘   └────┘   └────────┘   └────────┘
처리 활동 ▁▃▅█▅▃▁▃▅█                              + 메트릭 카드 6개(하단)
```

**센서 팜** — 타일 격자(영역에 맞춰 자동 크기) + 프리셋 6개

## 0. 세 화면의 역할

```
[센서 팜]  데이터를 만든다        →  악조건을 사람이 직접 만드는 도구
[관제실]   받아서 판정하고 저장한다 →  이 시스템의 서버
[상황판]   받아서 보여준다         →  소비자
```

**셋은 서로의 함수를 부르지 않는다.** MQTT 메시지로만 이어져 있다.
그래서 같은 것을 세는데도 값이 다를 수 있고, 그 차이가 정보가 된다.

# 1. 센서 팜

> 창 제목: `센서 팜 — IoT 데모`

## 1-1. 상단 — 연결과 조작

| 표시 | 값의 출처 | 갱신 | 뜻 |
|---|---|---|---|
| **`1,000대 · 실제 MQTT 발행`** | 고정 문구 | — | 가상 센서지만 **진짜 MQTT 로** 보낸다 |
| **연결 칩** (● 연결됨) | `publisher.IsConnected` | 매 UI 틱 | 🔒 매번 다시 묻는다. 한 번 켜고 두면 끊겨도 초록으로 남는다 |
| **⚡ 이상치 주입** | 버튼 | 클릭 시 | 물리적으로 불가능한 값(5,000)을 **실제로 발행**한다 |

### 이상치 주입이 「진짜 발행」인 이유

화면 숫자만 바꾸면 **관제실이 실제로 격리하는지 증명되지 않는다.**
진짜로 쏴야 관제실 정합 칩에 「격리 1건」이 뜨는 걸 확인할 수 있다.

## 1-2. 발신 레이트

```
발신 레이트   5,000 목표 · 실측 3,214/s     [정지][현실][정상][빠름][폭주][극한]
```

| 부분 | 뜻 |
|---|---|
| **목표** | 버튼으로 고른 값 |
| **실측** | 🔑 **실제로 나간 양**. 1초마다 `publisher.Published` 차이를 실제 경과 시간으로 나눈다 |

### 🔴 목표와 실측이 다른 게 정상이다

극한(20,000)은 **도달하지 못하는 값**이다. 메시지 1건 비용의 79% 가 주고받는 일이라
저장을 아무리 최적화해도 그 8% 안에서 움직인다.

> 그래서 **목표만** 보여주면 "왜 안 나오지?"가 되고,
> **실측만** 보여주면 무엇을 눌렀는지 모른다. 그래서 둘 다 쓴다.

### 프리셋 6개

| 버튼 | 값 | 무엇을 보는가 |
|---|---|---|
| 정지 | 0 | **부하가 없을 때 CPU 도 내려가는가** |
| 현실 | 분당 1건 | **정상 센서가 오프라인으로 안 잡히는가** (적응 임계) |
| 정상 | 17/s | 여유로운 정상 동작 |
| 빠름 | 500/s | 아직 여유 |
| 폭주 | 5,000/s | **워커가 실제로 늘어나는가** |
| 극한 | 20,000/s | **백로그가 쌓이고 폐기가 계수되는가** |

## 1-3. 가동률 (우상단)

```
99.9%
999 / 1,000
```

| 표시 | 계산 |
|---|---|
| 퍼센트 | `온라인 ÷ 전체 × 100` |
| 아래 줄 | `온라인 / 전체` |

🔑 **분자와 분모를 같이 보여준다.** 퍼센트만 있으면 「1,000대 중 몇 대인지」를 알 수 없다.

### 이 값은 「팜이 아는」 가동률이다

팜은 **자기가 발행 중인지**로 판단한다(타일을 클릭해 끈 센서만 오프라인).
관제실이 판정한 값과 **다를 수 있다** — §4 참조.

## 1-4. 센서 그리드 (본문)

타일 1,000개. 각 타일 = 센서 1대.

| 색 | 뜻 |
|---|---|
| 어두운 청록 | FLIR · 온라인 · 지금은 조용 |
| 어두운 보라 | Milesight · 온라인 · 지금은 조용 |
| 밝은 청록/보라 | **방금 발행함**(펄스, 약 4프레임 유지) |
| 붉은색 | **오프라인**(클릭해서 끈 것) |

**타일 클릭 = 그 센서를 죽이거나 살린다.**

```
클릭 → 오프라인
   ↓ 발행이 멈추고 내부 링버퍼(600건)에 쌓인다
다시 클릭 → 온라인
   ↓ 쌓인 것을 원본 시각 그대로 백필
```

## 1-5. 하단 상태바

| 표시 | 뜻 |
|---|---|
| **`누적 발신 N (이번 세션)`** | ⚠ **세션 값**이다. 팜을 껐다 켜면 0부터 |
| **`유실 0`** / `유실 N건 (버퍼 상한 초과)` | 링버퍼가 넘쳐 버린 수 |
| **`백필 대기 N건`** | 지금 버퍼에 쌓여 있는 수 |
| **활력 표시등** (● 발행 ● 연결) | 백그라운드 루프가 살아 있는가 |

### 「누적 발신」에 (이번 세션)이 붙은 이유

관제실의 「누적 수신」은 **전체 기간**이다. 둘 다 정확한데 나란히 놓으면 값이 크게 달라 보인다.
실제로 **24배 차이**가 나서 「데이터가 유실됐다」로 읽힌 적이 있다.

### 「유실 0」을 쓸 수 있는 이유

**그걸 반증할 카운터가 있기 때문이다.** 링버퍼가 넘치면 실제로 세어져 경고색으로 바뀐다.
카운터 없이 「유실 0」이라고 쓰면 그건 거짓말이 될 준비가 된 문구다.

# 2. 관제실

> 창 제목: `관제실 — 라이브 파이프라인`

## 2-1. 상태 헤더

| 표시 | 출처 | 뜻 |
|---|---|---|
| **브로커 칩** | `broker.IsStarted` + `ingest.IsConnected` | 🔒 **매 틱 재검증** |
| **기준 HH:mm:ss** | 지금 시각 | 이 화면 숫자가 **몇 초 전 것인지** |

### 브로커 칩의 세 상태

| 표시 | 뜻 |
|---|---|
| 초록 `브로커 가동 · :5281 구독 중` | 브로커도 돌고 수집도 붙었다 |
| 호박 `브로커 가동 · 수집 연결 대기` | 브로커는 떴는데 수집 클라이언트가 아직 |
| 빨강 `브로커 정지` | 브로커가 안 떴다 |

## 2-2. 상태 칩 2개

### 센서 칩

```
● 센서 1,000 / 1,000 온라인
● 센서 950 / 1,000 · 미확인 50대
```

| 부분 | 계산 |
|---|---|
| 앞의 수 | 임계 시간 안에 신호가 온 센서 수 |
| **뒤의 수** | 🔑 **있어야 할 센서 명부** 크기(1,000) |
| 미확인 | 프로비저닝돼 있는데 **한 번도 신호가 없던** 수 |

### 🔴 분모가 「명부」인 것이 핵심이다

```
❌ 온라인 ÷ 지금까지 신호를 받아본 센서
✅ 온라인 ÷ (명부 ∪ 관측된 센서)
```

📌 관측 기반으로 뒀다가 **1,000대 중 50대가 무응답인데 950/950 = 100%** 를 띄운 적이 있다.
**처음부터 없는 것은 영원히 안 보인다.**

### 정합 칩

우선순위 순으로 하나만 보여준다:

| 순위 | 표시 | 뜻 |
|---|---|---|
| 1 | `과부하 폐기 N건` (빨강) | 🔴 큐가 넘쳐 **버렸다** — 데이터가 사라진 것 |
| 2 | `저장 실패 N건` (빨강) | 저장이 끝내 실패 |
| 3 | `격리 N · 거부 M` (호박) | 불가능한 값 격리 / 망가진 값 거부 |
| 4 | `정합 OK · 유실 0` (초록) | 위가 전부 0 |

### 과부하 폐기를 먼저 보여주는 이유

이상치 격리는 **한 건이 걸러진 것**이고, 과부하 폐기는 **데이터가 사라진 것**이다.
후자가 더 심각하므로 먼저 말한다.

## 2-3. 지표 카드 6개

| 카드 | 계산 | 정상 범위 |
|---|---|---|
| **수신 (메시지/s)** | (지금 수신 − 직전 수신) ÷ **실제 경과 시간** | 발행 속도에 따라 |
| **워커 (적응 /8)** | 지금 도는 워커 수 | 백로그 따라 1~8 |
| **백로그 (밀린 수)** | 큐에 대기 중인 수 | 여유 시 0 근처 |
| **처리 지연** | 판정 1건의 평균 소요(µs) | 수십~수백 µs |
| **누적 수신 (전체 기간)** | 받은 메시지 총수 | 계속 증가 |
| **누적 저장 (전체 기간)** | raw + 롤업 이벤트 총수 | **수신의 약 2배** |

### ⚠️ 「초당」을 계산하는 법

```
❌ (지금 − 직전) ÷ 타이머 간격     ← 타이머는 부하가 걸리면 밀린다
✅ (지금 − 직전) ÷ 실제 경과 시간
```

📌 타이머 델타를 그대로 「/s」라 불러 처리량이 **8배 과대 표시**된 적이 있다.
바쁠수록 밀리는데 나누는 값은 그대로여서, **바쁠수록 부풀려진다.**

### 누적 저장이 누적 수신의 2배인 이유

**메시지 1건 = 이벤트 2건**(들어온 사람 수 + 나간 사람 수).

## 2-4. 장애 조치 카드 · 활력 표시등

| 표시 | 뜻 |
|---|---|
| `활성 0건 · 정상 (정리 02:31)` | 마지막 유지보수 시각 |
| `⚠ 정리 실패: …` | 🔴 유지보수 루프가 실패 중 |
| 활력 ● 수집 ● 정리 ● 핑 | 세 백그라운드 루프의 생사 |

### 활력 표시등이 장식이 아닌 이유

📌 유지보수 루프가 예외를 통째로 삼켜 **계속 실패해도 아무도 몰랐던** 적이 있다.
DB 는 조용히 커지고 있었다.

| 점 | 멈추면 |
|---|---|
| 수집 | 데이터가 안 들어오는데 화면은 마지막 값 유지 |
| 정리 | DB 가 무한히 커짐 |
| 핑 | 죽은 센서를 영원히 못 찾음 |

# 3. 종합 상황판

> 창 제목: `IoT 센서 종합 상황판`

## 3-1. 권한 스코프 버튼

```
권한(I4)  [전체] [수도권본부] [영남본부] [강남점] [해운대점]
```

누르면 **보이는 데이터 범위가 바뀐다.**

| 버튼 | 보이는 것 |
|---|---|
| 전체 | 매장 12곳 전부 |
| 수도권본부 | 산하 6곳 |
| 강남점 | **자기 매장만** |

🔒 이건 **데이터 경계**이지 로그인이 아니다. 이번 범위에 인증은 없다.

## 3-2. KPI 4칸

| KPI | 계산 | 상한 |
|---|---|---|
| **누적 유입** | 권한 범위 안 매장들의 `in` 합 | 없음 |
| **누적 유출** | `out` 합 | 없음 |
| **온라인 센서** | `N / M` — M 은 **명부 기준** | **1,000** |
| **유입 이벤트** | 이 앱이 해석한 이벤트 총수 | 없음 |

### 🔑 「온라인 센서」만 상한이 있다

```
온라인 센서  350 / 1,000   ← 지금 몇 대인가.  상한 있음
유입 이벤트  73,164        ← 지금까지 몇 건인가.  끝없이 증가하는 게 정상
```

## 3-3. 피드 상태 칩

| 표시 | 뜻 |
|---|---|
| 호박 `연결 중…` | 아직 붙는 중 |
| 초록 `라이브 · 관제실 브로커 구독 중` | 실제 데이터를 받는 중 |
| 🔴 빨강 `⚠ 데모 모드 · 브로커에 붙지 못함` | **가짜 데이터로 도는 중** |

### 데모 모드를 반드시 표시하는 이유

브로커에 못 붙어 시뮬레이터로 도는데 화면이 그냥 숫자를 보여주면,
그건 **가짜 데이터를 실제인 것처럼** 그리는 것이다.

## 3-4. 매장별 상태 현황

| 열 | 뜻 |
|---|---|
| 매장 | 🔒 **프로비저닝 명부** 기준. 데이터가 안 와도 목록에 남는다 |
| 온라인 | `N / M` — M 은 그 매장에 **있어야 할** 센서 수 |
| 유입 / 유출 | 누적 |
| 상태 | 아래 참조 |

### 상태 문구

| 문구 | 조건 |
|---|---|
| `정상` | 전부 온라인 |
| `일부 오프라인 N대` | 일부만 |
| **`측정 불가 (전부 무응답)`** | 온라인 0 — 🔑 「0명 방문」이 아니라 **「모른다」** |
| `센서 없음` | 명부에 센서가 0대 |

### 🔴 매장이 목록에서 사라지면 안 되는 이유

📌 스트림에서 사이트를 못 받은 센서를 건너뛰었더니
센서가 전부 죽은 매장이 목록에서 **통째로 사라진** 적이 있다.

> **0 으로 표시되는 것보다 나쁘다** —
> 0 은 「손님이 없었구나」지만, 사라지면 **「그런 매장이 없구나」**가 된다.

# 4. 왜 세 화면의 숫자가 다른가

가장 헷갈리는 부분이다. **셋은 서로 다른 것을 본다.**

| 화면 | 온라인 판단 근거 |
|---|---|
| **센서 팜** | 내가 지금 발행하고 있는가 (**발신 기준**) |
| **관제실** | 데이터 + **핑 응답** (조용한 센서에게 직접 물어봄) |
| **상황판** | **데이터만** (핑을 안 보낸다) |

### 예시

```
센서 팜:  1,000 / 1,000    ← 아무도 안 껐다
관제실:   1,000 / 1,000    ← 핑에 다 응답했다
상황판:     350 / 1,000    ← 최근에 데이터가 온 건 350대뿐
```

**이 차이는 정보다.** 「발행은 되는데 (그 센서의) 데이터가 최근에 안 왔다」는 뜻이다.

| 언제 나오나 | 정상인가 |
|---|---|
| 「현실 모드」(분당 1건) | ✅ 정상 — 데이터가 원래 뜸하다 |
| 「극한」 | ✅ 정상 — 부하가 상한을 넘었다 |
| 「정상(17/s)」 | ⚠ **의심** — 발행이 밀리고 있다 |

> 🔒 억지로 맞추지 않는다. 같아지게 만들면 그 차이가 주던 정보가 사라진다.

# 5. 갱신 주기 — 화면마다 다르게 그린다

모든 화면이 같은 규칙을 쓴다.

| 상황 | 간격 |
|---|---|
| 보고 있고 값도 움직임 | 33ms (30fps) |
| 보고는 있지만 조용함 | 125ms (8fps) |
| 창이 뒤에 있음 | 500ms (2fps) |
| 애니메이션 끔 | 1,000ms (1fps) |

📌 부하가 15 msg/s 뿐인데 세 앱이 **CPU 314%** 를 쓰던 원인이
「부하와 무관하게 항상 33ms」였다.

> 🔑 **「이 시스템은 효율적이다」라고 말하려면 부하가 없을 때 CPU 도 내려가야 한다.**

## 화면이 갱신되는 경로

```
[백그라운드]  발행 스레드 · 수집 워커 · 유지보수 루프
       ↓  카운터만 올린다 (Interlocked)
[UI 타이머]   그 카운터를 읽어 화면에 쓴다
```

🔒 **백그라운드가 화면을 직접 건드리지 않는다.**
화면은 **읽기만** 한다 — 그래야 어느 쪽이 느려도 다른 쪽이 안 멈춘다.

# 6. 화면만 보고 검산하는 법

```
① 관제실 누적 저장  ≈  누적 수신 × 2
② 상황판 유입 이벤트  ≈  관제실 누적 저장
③ 온라인 센서  ≤  1,000
④ 매장별 온라인 합  =  전체 온라인
```

하나라도 깨지면 **버그다.**

## 1. "브로커를 앱 안에 넣는다"

### MQTT 는 직접 통신이 아니다

보내는 쪽과 받는 쪽이 서로를 모른다. 가운데 **중개자(broker)** 만 안다.

```
   센서 ──발행(publish)──▶  [ 브로커 ]  ──전달──▶  구독자(subscribe)
                            토픽별로 분류
```

센서는 "누가 받는지" 모르고, 대시보드는 "누가 보내는지" 모른다.
둘 다 **토픽 이름**만 안다 — `sensors/flir/store-01/flir-0001` 같은 주소.

> 이걸 **발행/구독(pub-sub)** 이라 한다.
> 장점: 받는 쪽이 몇 개든, 나중에 하나 더 붙든, 보내는 쪽 코드를 안 고쳐도 된다.

### 보통은 브로커가 "따로 설치하는 프로그램"이다

```
[ 센서 앱 ]  ─┐
              ├─▶  [ Mosquitto.exe ]   ← 별도 설치 · 별도 프로세스 · 설정 파일
[ 대시보드 ] ─┘         (브로커)
```

Mosquitto · EMQX · HiveMQ 같은 것들이 그렇다. 서버에 설치하고, 설정하고, 서비스로 띄운다.

### 우리는 브로커를 **라이브러리로** 가져다 쓴다

MQTTnet 은 브로커 기능을 **C# 코드에서 직접 띄울 수 있게** 제공한다.
그래서 관제실 프로그램이 시작될 때, **자기 프로세스 안에서** 브로커를 켠다.

```
┌─────────── ControlRoom.exe (프로세스 하나) ───────────┐
│                                                       │
│   [ 브로커 ]  ← 127.0.0.1:5281 포트를 열고 있다        │
│       │                                               │
│       ▼                                               │
│   [ 수집 · 판정 · 저장 ]                               │
│                                                       │
└───────────────────────────────────────────────────────┘
              ▲                        ▲
              │ TCP 접속                │ TCP 접속
       [ SensorFarm.exe ]        [ Dashboard.exe ]
```

**바깥에서 보면 똑같다.** 다른 앱들은 여전히 "5281 포트에 TCP 로 접속"할 뿐,
그 포트를 여는 게 별도 서버인지 관제실 내부인지 알 필요가 없다.

> 🏢 **비유**: 우체국을 따로 세우는 대신, 사무실 안에 우편 분류실을 두는 것.
> 편지를 부치는 사람 입장에서는 달라지는 게 없다.

### 왜 이렇게 했나

| | 별도 브로커 | 앱 내장 |
|---|---|---|
| 실행 준비 | 설치 → 설정 → 서비스 등록 | **exe 실행** |
| 시연 | "먼저 Mosquitto 를 설치하시고…" | 그냥 켜면 된다 |
| 검증 | 환경이 다르면 결과도 다름 | 어디서 돌려도 같다 |

> 🔑 **재현성**이 이유다.
> "설치 안내서를 먼저 읽어야 실행되는" 시스템은 시연도 검증도 어렵다.

### 대신 치르는 값 (정직하게)

- **관제실이 죽으면 통신 전체가 끊긴다.** 브로커가 그 안에 있으니까.
  → 그래서 나머지 앱은 **연결될 때까지 무한 재시도**한다. 관제실이 돌아오면 자동 복구.
- **브로커 CPU 를 수집 서버와 나눠 쓴다.**
  실측하면 메시지 1건 처리 비용의 **38% 가 브로커 라우팅**, 41% 가 QoS1 확인 응답이다.
  즉 **비용의 79% 가 "주고받는 일"** 이고 실제 처리는 8% 다.
  → 센서가 1만 대를 넘어가면 브로커를 **별도 호스트로 분리**하는 게 첫 번째 개선이다.
  코드를 안 고쳐도 되고, 실운영 구조와도 같아진다.

## 2. 코덱 (codec) = 형식 번역기

### 이름의 유래

**co**der + **dec**oder. 원래는 영상·음성 압축 형식(H.264, MP3)을 다루는 말이지만,
여기서는 **"바깥 형식 ↔ 우리 형식" 변환기**라는 뜻으로 쓴다.

### 왜 필요한가 — 제조사마다 말투가 다르다

같은 사실을 두 센서가 이렇게 말한다.

**FLIR 이 하는 말**
```json
{
  "sensorId": "flir-0001",
  "timestamp": "2026-07-09T09:00:00+09:00",
  "lines": [ { "direction": "in",  "count": 3 },
             { "direction": "out", "count": 2 } ]
}
```

**Milesight 가 하는 말**
```json
{
  "deviceId": "milesight-0002",
  "time": "2026-07-09T09:00:00+09:00",
  "periodIn": 3,
  "periodOut": 2
}
```

**둘 다 뜻은 같다** — "9시에 3명 들어오고 2명 나갔다".
그런데 필드 이름도(`sensorId` vs `deviceId`), 구조도(배열 vs 개별 필드) 다르다.

> ☕ **비유**: 손님이 "아아", "아이스 아메리카노", "차가운 아메리카노" 라고 제각각 말해도
> 주방에는 **하나의 메뉴 코드**로 들어가야 한다. 코덱이 그 번역을 한다.

### 코덱이 하는 일

```
   FLIR JSON ──▶ [ FlirCodec ] ─────┐
                                    ├──▶  CountEvent  (표준 형식)
Milesight JSON ─▶ [ MilesightCodec ]┘
```

번역 결과는 **완전히 같은 타입**이다.

```
CountEvent { SensorId, OccurredAt, Count, Direction }
```

그래서 **시스템의 나머지 전부는 제조사를 모른다.**
저장소도, 집계도, 화면도 `CountEvent` 만 안다.

### 새 제조사가 들어오면

```
1. AxisCodec 클래스 하나 작성
2. 등록 한 줄 추가
3. 끝 — 다른 파일은 손대지 않는다
```

이게 "플러그인 구조"의 실제 모습이다.

### 🔒 코덱이 지키는 두 가지

**① 번역만 한다. 판정하지 않는다.**

값이 이상해도(`-5`, `99999`) 코덱은 그대로 넘긴다. 판정은 다음 단계 몫이다.

> **왜**: 번역기마다 판정 로직을 넣으면, 새 제조사를 추가할 때마다
> **규칙이 깨질 기회가 하나씩 늘어난다.** 규칙은 한 곳에만 있어야 한다.

**② 절대 예외를 던지지 않는다.**

JSON 이 깨졌든 필드가 없든, 코덱은 **빈 결과**를 돌려줄 뿐 프로그램을 멈추지 않는다.

> **왜**: 밖에서 온 **한 건의 망가진 메시지**가 수집 루프 전체를 멈추면 안 된다.
> 관대해서가 아니라, 한 건의 불량이 전체를 죽이지 못하게 하는 **가용성 장치**다.
>
> 단, 한 라인이 깨져도 **나머지 형제 라인은 살린다** —
> `out` 만 깨졌다고 `in` 까지 버리면 **데이터가 있는데 안 세게** 된다.

## 3. 큐 이후 — 워커가 꺼낸 다음 무슨 일이 벌어지나

### 전체 순서

```
 ①            ②           ③          ④          ⑤
브로커  ──▶  큐  ──▶  워커가 꺼냄 ──▶ 코덱 ──▶ 판정 ──▶ 저장소
 수신       완충재      일꾼        번역      검사       기록
```

### ① ~ ② 왜 큐가 필요한가

**받는 속도와 처리하는 속도가 다르다.**

- 받기: 네트워크에서 바이트를 읽는 것 — 빠르다
- 처리: JSON 해석 + 검사 + 디스크 저장 — 느리다

받는 쪽이 처리 끝날 때까지 기다리면 **뒤 메시지들이 밀린다.**
그래서 일단 큐에 던져 넣고 즉시 다음 메시지를 받는다. 큐가 **완충재**다.

> 큐(Queue) = **대기열**. 먼저 들어온 게 먼저 나간다(**FIFO**, 선입선출).
> 은행 번호표와 같다.

### 우리 큐의 특이한 점 두 가지

**① 크기가 정해져 있다 (15만 칸)**

무한 큐는 만들 수 없다. 메모리가 유한하니까.

**② 가득 차면 "가장 오래된 것"을 버린다**

```
   가득 찬 큐
   [오래된] ■■■■■■■■■■■■■■■■ [최신]
      ↑
   여기서 버린다              ← 새 메시지는 여기로 들어온다
```

보통은 "가득 차면 넣는 쪽이 기다린다"로 만든다. 그런데 그러면:

```
큐가 가득참 → 받는 쪽이 기다림 → 브로커에 응답이 늦음
   → 브로커가 "못 받았나 보다" 하고 재전송 시작
      → 재전송이 큐를 더 채움 → 영원히 안 풀림
```

**막히면 더 막히는** 구조가 된다. 그래서 **버리는 쪽**을 택했다.

> 🔴 **단, 버렸으면 반드시 센다.**
> 이 종류의 버림은 코드 어디에도 흔적이 안 남는다 — 함수는 "성공"을 돌려주니까.
> 그래서 별도 카운터를 달고 **화면에 표시**한다.
> 버리는 것 자체는 설계고, **버린 걸 숨기는 게** 문제다.

### ③ 워커 — 큐에서 꺼내 일하는 일꾼

**워커 = 스레드 하나.** 프로그램 안에서 독립적으로 도는 작업 흐름이다.

```
        ┌─▶ [워커 1] ─┐
  큐 ───┼─▶ [워커 2] ─┼─▶ 저장소
        └─▶ [워커 3] ─┘
```

**개수는 1~8개 사이에서 자동 조절**된다. 큐가 밀리면 늘리고, 한가하면 줄인다.

> 🔑 **워커에 낮은 우선순위를 준다.**
> 서버가 아무리 바빠도 **화면은 멈추면 안 되기** 때문이다.
> 처리량은 남는 CPU 로 흡수하되, 워커가 잃는 것은 **"화면을 밀어낼 권리"뿐**이다.

### ④ 배치 — 한 번에 최대 512건씩 묶는다

워커는 큐에서 하나씩 꺼내지 않는다. **지금 당장 꺼낼 수 있는 만큼** 한꺼번에 꺼낸다.

**왜 묶나 — 저장 비용 때문이다.**

DB 에 1건씩 저장하면 매번 "디스크에 확실히 썼는지" 확인하는 절차가 붙는다.
이게 비싸다. 실측:

| 방식 | 처리량 |
|---|---|
| 1건씩 저장 | 16,941 건/초 |
| 묶어서 저장 | **277,650 건/초** |

**16.4배**다. 묶지 않으면 워커를 아무리 늘려도 **저장 단계에서 한 줄로 서게** 되어
처리량이 안 오른다 — 자동 조절 워커가 장식이 된다.

**단, 모으려고 기다리지는 않는다.**

```
❌ "512개 찰 때까지 기다렸다가 저장"  → 한가할 때 지연이 커진다
✅ "지금 꺼낼 수 있는 것까지만 묶는다"  → 한가하면 배치 크기가 1이 된다
```

### ⑤ 판정 — 받아들일 것인가

```
비어 있나?          → ❌ Rejected     (데이터가 망가짐)
센서 ID 가 있나?     → ❌ Rejected
0 ~ 100만 범위인가?  → ❌ Rejected     (오버플로 방지)
100 이하인가?        → ⚠️ Implausible (물리적으로 불가능 → 격리하고 센다)
이미 저장됐나?       → 🔁 Duplicate   (정상 — 재전송은 당연히 일어난다)
                    → ✅ Appended
```

### 🔴 배치가 만드는 문제 하나

배치는 **전부 되거나 전부 안 되거나**(원자적)다.
그래서 512건 중 **한 건이 실패하면 512건 전부 롤백**된다.

1건씩 저장했다면 앞의 511건은 이미 저장돼 살아남았을 것들이다.
즉 **묶는 것이 오류 시 손실 반경을 512배로 키운다.**

**대응**: 배치가 실패하면 **1건씩 다시 시도해 구제**하고, 끝내 못 살린 것만 센다.

## 4. 한눈에 다시

```
[센서]     "9시에 3명 들어옴"을 제조사 방언으로 말한다
   │
   ▼  MQTT 발행
[브로커]   토픽으로 분류해 구독자에게 전달        ← 관제실 앱 안에 들어 있다
   │
   ▼  구독 콜백 (즉시 반환해야 함)
[큐]       완충재. 15만 칸. 넘치면 오래된 것부터 버리고 센다
   │
   ▼  워커 1~8개가 꺼냄 (최대 512건 묶음)
[코덱]     제조사 방언 → 표준어(CountEvent)      ← 번역만, 판정 안 함, 예외 안 던짐
   │
   ▼
[판정]     받아들일지 5단계로 결정                ← 규칙은 여기 한 곳에만
   │
   ▼
[저장소]   append-only. 한 번 들어간 건 안 바뀐다
```

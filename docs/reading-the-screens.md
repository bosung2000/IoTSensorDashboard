# 화면 읽는 법 — 무엇이 정상이고 무엇이 이상인가

> 돌려 보다가 **"이 숫자가 맞는 건가?"** 싶을 때 보는 문서.
>
> 이 시스템은 「조용히 틀리는 것」을 막으려고 만들었지만,
> 그러다 보니 화면에 숫자가 많아졌고 **어느 게 정상인지 헷갈리기 쉽다.**

---

## 1. 먼저 — 값의 두 종류를 구분한다

가장 흔한 혼동이 이것이다.

| 종류 | 예 | 상한 | 계속 늘어나면 |
|---|---|---|---|
| **지금 몇 개인가** | `온라인 센서 350 / 1,000` | **있다** (1,000) | ⚠ 이상 |
| **지금까지 몇 건인가** | `유입 이벤트 73,164` | **없다** | ✅ **정상** |

```
온라인 센서  350 / 1,000    ← 센서 수. 1,000이 최대
유입 이벤트  73,164         ← 누적 건수. 끝없이 증가하는 게 정상
누적 수신    36,505         ← 누적 메시지 수
누적 저장    73,010         ← 누적 이벤트 수
```

### 🔑 누적 수신과 누적 저장이 2배 차이 나는 건 정상이다

```
메시지 1건  =  이벤트 2건 (in + out)

누적 수신 36,505  ×2  =  누적 저장 73,010  ✅
```

한 센서가 한 번 보고할 때 **들어온 사람 수와 나간 사람 수를 같이** 보내기 때문이다.

### 라벨의 「(전체 기간)」과 「(이번 세션)」

| 화면 | 값 | 기간 |
|---|---|---|
| 관제실 「누적 **저장**」 | **전체 기간** | 프로그램을 껐다 켜도 **안 줄어든다**(I6 — DB 에 남는다) |
| 관제실 「누적 **수신**」 | **이번 세션** | 관제실을 껐다 켜면 **0부터** (메모리 카운터) |
| 센서 팜 「누적 발신」 | **이번 세션** | 팜을 껐다 켜면 **0부터** |

📌 셋 다 정확한데 나란히 놓으면 크게 달라 보인다.
실제로 `누적 수신 1,861` 옆에 `누적 저장 1,763,920` 이 붙어
「데이터가 유실됐다」로 읽힌 적이 있어서, 라벨에 기간을 박아 두었다.

> ⚠️ 이 문서는 한때 「누적 수신 = 전체 기간」이라고 적고 있었는데 **틀린 설명**이었다.
> 그 카운터는 DB 에서 복원하지 않는다. 문서가 코드보다 오래 살아남아 생긴 오류다.

## 1-2. 「응답률」과 「수신율」은 다른 것을 잰다

관제실 가운데에 비율이 **두 개** 있다. 헷갈리기 쉬운데, 둘의 차이가 곧 정보다.

| 지표 | 재는 것 | 언제 100% 인가 |
|---|---|---|
| **센서 응답률** | 살아 있는가 (**핑 응답 포함**) | 센서가 전원만 들어와 있어도 |
| **데이터 수신율** | 실제로 **보내고 있는가** | 최근에 데이터를 준 센서만 |

```
센서 응답률 100.00%      데이터 수신율   0.00%    ← 발신이 멈춤
1,000/1,000 · 응답(핑)   0/1,000 · 실제 발신 중

센서 응답률 100.00%      데이터 수신율  20.40%    ← 17/s 로 느리게 발신 중
```

**두 값의 차이 = 살아 있지만 안 보내는 센서 수.**

> 🔑 이 둘을 한 지표로 합치면 「데이터가 0 건인데 화면은 완벽」인 상태가 만들어진다.
> 실제로 그랬고, 그래서 나눴다.

📌 **데이터 수신율이 낮다고 곧 장애는 아니다.** 느린 센서는 원래 뜸하게 보낸다
(17/s 프리셋이면 센서당 59초에 한 번). 그래서 색도 빨강이 아니라 파랑/노랑으로만 쓴다.

---

## 1-3. 「끊김」과 「미관측」은 다르다

대시보드 `온라인 센서` 아래에 작은 글씨가 붙는다.

```
온라인 센서 (I5 · 수신 기준)
   203 / 1,000
끊김 130 · 미관측 667
```

| 표시 | 뜻 | 누가 처리하나 |
|---|---|---|
| **끊김** | 보다가 신호가 멈춤 | 장애 조치 — 알림·에스컬레이션 |
| **미관측** | **한 번도 못 봄** | 설치·배선·명부 확인 |

🔑 **기동 직후엔 미관측이 대부분인 게 정상이다.**
센서 1,000대를 17건/s 로 돌리면 한 바퀴에 약 59초,
게다가 침묵 허용치가 **관측된 주기에서 나오므로**(주기 × 2.5) 주기를 알려면 두 번 봐야 한다.
→ **약 2분**이 지나야 전부 온라인으로 자리잡는다. 그동안의 낮은 숫자는 장애가 아니다.

---

## 1-4. 「중복」은 0 이 정상이 아니다 (하지만 크면 사고다)

관제실 정합 칩과 파이프라인 「중복 접음」 노드에 나온다.

| 상황 | 판정 |
|---|---|
| 0 ~ 수신량의 몇 % | ✅ 정상 — 재전송은 늘 있다(I1 이 접는 게 제 일) |
| **수신량에 육박** | 🔴 **사고** — 같은 데이터를 반복 발행하고 있다 |

📌 실제로 이게 **저장이 0 이 되는 원인**이었다.
발행 측이 한 틱에 같은 센서를 여러 번 세면 멱등 키가 겹쳐 전부 접힌다.
그때 백로그도 폐기도 0 이라 **화면 어디에도 흔적이 없었다** — 그래서 이 카운터를 올렸다.

> **계산 오류보다 이런 의미 불일치가 숫자 신뢰를 더 크게 깨뜨린다.**

## 2. 세 화면이 서로 다를 때 — 대부분 정상이다

같은 것을 세는데 값이 다르면 불안하지만, **셋은 서로 다른 것을 본다.**

| 화면 | 무엇으로 판단하나 | 그래서 |
|---|---|---|
| **센서 팜** | 자기가 발행하고 있는가 (**발신 기준**) | 팜이 아는 「살아있음」 |
| **관제실** | 데이터 + **핑 응답** (조용한 센서에게 직접 물어봄) | 가장 정확 |
| **상황판** | **데이터만** (핑을 안 보냄) | 데이터가 뜸하면 낮게 나옴 |

### 예: 관제실 1,000 / 상황판 350

```
관제실:  센서 1,000 / 1,000 온라인    ← 핑에 다 응답했다
상황판:  온라인 센서 350 / 1,000      ← 최근에 데이터가 온 건 350대뿐
```

**이 차이 자체는 정보다.** 「발신은 되는데 (그 센서의) 데이터가 최근에 안 왔다」는 뜻이다.

| 상황 | 정상인가 |
|---|---|
| 「현실 모드」(분당 1건)에서 차이가 큼 | ✅ **정상** — 데이터가 원래 뜸하다 |
| 「정상(17/s)」에서 차이가 큼 | ⚠ **의심** — 발행이 밀리고 있다 |
| 「극한」에서 차이가 큼 | ✅ 정상 — 부하가 상한을 넘었다는 뜻 |

> 🔒 억지로 맞추지 않는다. 두 값이 같아지도록 만들면 그 차이가 주던 정보가 사라진다.

## 3. 프리셋별로 무엇을 봐야 하나

### 정지

```
발신 레이트  정지
수신         0 msg/s
```

✅ 아무 일도 안 일어나는 게 정상. **CPU 사용률이 내려가는지** 확인.

### 현실 (분당 1건)

```
발신 레이트  현실 · 실측 16/s
관제실 센서  1,000 / 1,000 온라인   ← 🔑 여기가 핵심
```

🔑 **정상 센서가 오프라인으로 안 잡히는지**를 본다.
고정 임계(12초)였다면 이 모드에서 **전부 오프라인**이 된다.
관측된 주기에 맞춰 임계가 늘어나기 때문에 정상으로 유지된다.

### 정상 (17/s) · 빠름 (500)

```
수신         목표와 비슷
백로그       0 근처
워커         1
과부하 폐기  0
```

✅ 여유롭게 처리되는 구간. **백로그가 안 쌓이는 게** 정상.

### 폭주 (5,000)

```
백로그       쌓이기 시작
워커         2, 3, … 로 증설
처리 지연    올라감
```

🔑 **워커가 실제로 늘어나는지**를 본다. 백로그가 300을 넘으면 1초 안에 증설된다.

### 극한 (20,000)

```
발신 레이트  20,000 목표 · 실측 3,000~5,000/s   ← ⚠ 목표에 도달하지 않는다
백로그       계속 쌓임
과부하 폐기  N건 (경고색)
```

### 🔴 극한은 「달성하는」 값이 아니다

목표 20,000 에 도달하지 못하는 것이 **정상**이다.

📌 메시지 1건의 비용을 뜯어보면:

| 항목 | 비중 |
|---|---|
| QoS1 확인 응답 왕복 | **41%** |
| 브로커 라우팅 | **38%** |
| TLS 암·복호 | 13% |
| **실제 처리**(해석 + 저장) | **8%** |

**비용의 79% 가 「주고받는 일」**이다. 저장을 아무리 최적화해도 그 8% 안에서 움직인다.

> 극한 프리셋의 목적은 처리량 자랑이 아니라
> **「한계를 넘으면 무슨 일이 일어나는가」를 눈으로 보여주는 것**이다.
>
> 봐야 할 것: **백로그가 쌓이고 · 워커가 늘고 · 폐기가 카운터에 잡히고 · 그런데도 화면이 계속 갱신되는가.**

## 4. 🔴 이건 진짜 이상 신호다

위와 달리, 아래는 **정상이 아니다.**

| 증상 | 무엇이 문제인가 |
|---|---|
| **센서 팜 화면이 멈춤** | 발행이 UI 스레드를 잡아먹고 있다 |
| **극한인데 백로그가 0** | 발행이 목표 근처도 못 가고 있다(병목이 발행 측) |
| **극한인데 워커가 1개 고정** | 증설 로직이 안 돈다 |
| **「유실 0」인데 값이 안 맞음** | 어딘가에서 조용히 버리고 있다 |
| **브로커 칩이 초록인데 수신 0** | 상태 표시가 1회성 주장이다 |
| **상황판이 「데모 모드」인데 숫자가 나옴** | 정상 — 다만 **그게 가짜 데이터**라는 뜻이다 |
| **매장이 목록에서 사라짐** | 목록을 「데이터가 온 매장」으로 만들고 있다 |
| **가동률 100.000%인데 센서가 죽어 있음** | 분모가 「관측된 것」이다 |

### 실제로 이 중 셋이 났었다

> **2026-08-05** — 극한 프리셋에서
>   · 센서 팜 화면이 멈춤
>   · 실측 발행량이 483/s (목표의 2.4%)
>   · 관제실 온라인 수가 1,000 → 400 으로 널뜀
>
> 원인: 발행 루프가 UI 스레드에서 **순차로 답을 기다리며** 돌고 있었다.
> 관제실 워커는 전용 스레드로 뺐으면서 발행 측은 안 뺀 것.
>
> 고친 뒤 실측: **26,445 msg/s**(54배), 유실 0.

## 5. 값이 서로 맞는지 스스로 검산하는 법

화면만 보고도 **모순을 잡을 수 있다.**

```
① 누적 저장  ≈  누적 수신 × 2
   (메시지 1건 = in/out 이벤트 2건)

② 상황판 「유입 이벤트」  ≈  관제실 「누적 저장」
   (같은 브로커를 보므로 비슷해야 한다. 상황판이 늦게 떴으면 그만큼 적다)

③ 온라인 센서 ≤ 1,000
   (넘으면 명부 밖 센서가 섞인 것)

④ 매장별 온라인 합  =  전체 온라인
   (안 맞으면 어느 매장이 목록에서 빠진 것)
```

이 중 하나라도 깨지면 **버그다.** 고부하 통관 테스트가 이 등식들을 자동으로 검사한다:

```
수신 = 처리 + 폐기        ← 어느 것도 조용히 사라지지 않는다
```

## 6. 로그 보는 법

```
%LOCALAPPDATA%\IoTSensorDashboard\logs\
    controlroom.log
    sensorfarm.log
    dashboard.log
    *.log.1          ← 직전 파일(5MB 넘으면 밀린다)
```

형식:

```
2026-08-05 02:31:07.412	ERR	farm.publish	발행 루프 오류	InvalidOperationException: ...
        at ...
        at ...
```

| 태그 | 뜻 |
|---|---|
| `INF` | 기동·종료·설정 변경 |
| `WRN` | 계속 도는 데 문제없지만 알아야 할 것 |
| `ERR` | 실패. **여기가 있으면 화면 카운터도 함께 확인** |

### 어디를 먼저 보나

| 증상 | 볼 곳 |
|---|---|
| 데이터가 안 흐름 | `sensorfarm.log` 의 `farm.publish` · `controlroom.log` 의 `server.worker` |
| 앱이 조용히 죽음 | 각 로그 끝부분 (`=== 종료 ===` 이 없으면 비정상 종료) |
| 숫자가 이상함 | `server.scale`(워커 증감) · `farm.rate`(레이트 변경) 시각과 대조 |
| 화면이 멈춤 | 로그는 계속 쓰이는지 확인 — **쓰이면 UI 문제, 안 쓰이면 백엔드 문제** |

> 🔑 마지막 항목이 특히 쓸모 있다.
> 「멈췄다」일 때 연결부터 의심하면 시간을 버린다 —
> **로그가 계속 늘어나면 백엔드는 살아 있는 것**이고, 문제는 화면이다.

---

## 7. 한 줄 요약

> **상한이 있는 값**(온라인 센서)과 **누적 값**(이벤트 수)을 먼저 구분한다.
> 세 화면이 다른 건 대부분 **서로 다른 것을 보기 때문**이다.
> 극한은 **도달하는 값이 아니라 한계를 보여주는 장치**다.
>
> 진짜 이상 신호는 하나다 — **화면이 멈추거나, 숫자끼리 모순되거나, 카운터 없이 「정상」이라고 쓰여 있을 때.**

# 저장 층 상세 — 데이터가 들어와서 나가기까지

> 2층에서 만든 것을 **용어부터** 풀어 쓴다.
> DB 를 처음 다루는 사람도 "무엇이 어디에 어떻게 저장되고, 왜 그렇게 했는지"를 알 수 있게.

---

## 0. 이 층이 정확히 무엇인가

"DB 구조"라고 부를 수 있지만, 정확히는 **세 가지**를 만들었다.

| # | 무엇 | 대답하는 질문 |
|---|---|---|
| ① **스키마** (구조) | 테이블 4개와 각 칸의 모양 | 데이터를 **어떤 모양으로** 담을 것인가 |
| ② **저장 규칙** | 어떻게 넣고, 언제 정리하고, 무엇을 보장하는가 | 넣는 **방법과 약속** |
| ③ **조회 방법** | 어떤 질문에 어떻게 답하는가 | 담은 걸 **어떻게 꺼내 쓸 것인가** |

구조만 있으면 "그릇"이고, 규칙까지 있어야 **"믿을 수 있는 그릇"**이 된다.
이 프로젝트에서 중요한 건 후자다.

---

## 1. 기초 용어 — 표를 예로

DB 는 결국 **표(table)** 다. 엑셀 시트를 떠올리면 된다.

```
                    ┌─── 열(column) ───────────────────────┐
                    │ dedup_key │ sensor_id │ count │ ...  │
   행(row) ────────▶│ flir-1|…  │ flir-0001 │   3   │      │
   행(row) ────────▶│ flir-1|…  │ flir-0001 │   2   │      │
                    └──────────────────────────────────────┘
```

| 용어 | 뜻 | 우리 예 |
|---|---|---|
| **테이블(table)** | 표 하나 | `events` · `events_hourly` · `outages` · `audit` |
| **열(column)** | 표의 세로 칸. 이름과 자료형이 있다 | `count INTEGER` — 정수만 들어감 |
| **행(row)** | 표의 가로 한 줄. 데이터 한 건 | 이벤트 한 개 |
| **스키마(schema)** | 표들의 설계도. "어떤 테이블에 어떤 열이 있는가" | `CREATE TABLE …` 문 전체 |
| **DDL** | 구조를 정의하는 SQL (`CREATE`, `ALTER`) | 우리 `SqliteSchema.cs` |
| **DML** | 데이터를 다루는 SQL (`INSERT`, `SELECT`, `DELETE`) | 나머지 전부 |

### `NULL` — "값이 없음"

빈 문자열(`""`)이나 0 과 **다르다.** "아직 모른다 / 해당 없음"이라는 별개의 상태다.

```
direction = "in"   →  들어옴
direction = ""     →  빈 문자열이라는 값
direction = NULL   →  방향 정보가 아예 없음
```

우리 `events` 테이블에서 `direction` 은 `NULL` 을 허용한다 —
방향을 보고하지 않는 센서가 있을 수 있기 때문이다.

> ⚠️ 그런데 `events_hourly` 에서는 **`NULL` 을 금지하고 빈 문자열을 쓴다.**
> 이유는 §3 에서 설명한다. (미리 말하면: SQL 에서 `NULL` 은 비교가 애매하다)

## 2. 기본키(PRIMARY KEY) — 이 시스템의 핵심 장치

### 기본키란

> **그 행을 유일하게 식별하는 열.** 같은 값이 두 번 들어올 수 없다.

주민등록번호 같은 것이다. 이름은 겹칠 수 있지만 주민번호는 못 겹친다.

### 🔑 우리는 이걸 "중복 방지 장치"로 쓴다

```sql
CREATE TABLE events(
    dedup_key   TEXT PRIMARY KEY,   ← 여기
    ...
);
```

`dedup_key` 는 이렇게 만든다.

```
센서ID | 발생시각(밀리초) | 방향
flir-0001|1783414800000|in
```

같은 센서가 같은 순간에 같은 방향으로 보고한 것은 **논리적으로 같은 이벤트**다.
그러니 키가 같고, **DB 가 두 번째 것을 자동으로 거부한다.**

### ❌ 이렇게 하면 안 된다

```
1. SELECT 로 "이미 있나?" 확인
2. 없으면 INSERT
```

**두 스레드가 동시에 1번을 통과할 수 있다.** 둘 다 "없네" 하고 둘 다 넣는다.

```
스레드 A: 확인… 없음     스레드 B: 확인… 없음
스레드 A: 넣기 ✓         스레드 B: 넣기 ✓      ← 두 번 세어짐
```

### ✅ 우리 방식

```sql
INSERT OR IGNORE INTO events(...) VALUES(...);
```

**"넣되, 키가 이미 있으면 조용히 무시하라"** — 이 판단을 DB 가 **원자적으로** 한다.

> **원자적(atomic)** = "쪼갤 수 없다". 확인과 삽입 **사이에 끼어들 틈이 없다.**
> 이 단어는 트랜잭션에서 또 나온다.

그리고 결과는 이렇게 읽는다.

| `ExecuteNonQuery()` 반환값 | 뜻 | 판정 |
|---|---|---|
| `1` | 한 행이 새로 들어감 | `Appended` |
| `0` | 이미 있어서 무시됨 | `Duplicate` |

**"몇 행이 바뀌었나"가 곧 판정**이다. 별도 조회가 필요 없다.

## 3. 테이블 4개 — 각 칸이 왜 있는가

### ① `events` — 원본 이벤트 (보존창 3시간)

```sql
CREATE TABLE events(
    dedup_key   TEXT PRIMARY KEY,   -- 중복 방지 (I1)
    sensor_id   TEXT NOT NULL,      -- 어느 센서
    occurred_at TEXT NOT NULL,      -- 언제 (ISO-8601 문자열)
    count       INTEGER NOT NULL,   -- 몇 명
    direction   TEXT                -- in / out / NULL
);
```

| 설계 결정 | 이유 |
|---|---|
| 시각을 **문자열**로 저장 | SQLite 에는 날짜 타입이 없다. ISO-8601 은 **사전순 = 시간순**이라 문자열 비교로 정렬·범위 조회가 된다 |
| **`seq` 컬럼 없음** | 예전에 삽입 순서용 컬럼이 있었는데, 넣을 때마다 `MAX(seq)` 전체 스캔이 일어나 **O(n²)** 였다. SQLite 내장 `rowid` 가 이미 삽입 순서를 보존한다 |
| **인덱스 없음** | 아래 참조 |

### 🔴 인덱스를 일부러 안 만들었다

**인덱스(index)** = 책의 색인. 특정 값을 빨리 찾게 해 주는 별도 자료구조다.

```
인덱스 없음 : 처음부터 끝까지 훑는다        (느린 조회)
인덱스 있음 : 색인을 보고 바로 찾는다        (빠른 조회)
```

**그런데 공짜가 아니다.**

```
INSERT 할 때마다 색인도 같이 갱신해야 한다  →  삽입이 느려진다
```

우리는 **초당 수천 건을 넣고**, 조회는 **보존창(3시간) 안의 작은 범위**뿐이다.
그래서 삽입 속도를 택했다.

> 📌 **"인덱스는 무조건 좋다"가 아니다.** 읽기가 많으면 이득, 쓰기가 많으면 손해다.
> 우리는 압도적으로 쓰기가 많다.

### ② `events_hourly` — 롤업 (오래된 원본이 접혀 들어오는 곳)

```sql
CREATE TABLE events_hourly(
    sensor_id   TEXT NOT NULL,
    hour        TEXT NOT NULL,      -- '2026-07-09T09:00:00+00:00'
    direction   TEXT NOT NULL,      -- '' = 방향 없음  ⚠ NULL 금지
    count_sum   INTEGER NOT NULL,   -- 그 시간대 합계
    event_count INTEGER NOT NULL,   -- 그 합계를 만든 원본 건수
    PRIMARY KEY(sensor_id, hour, direction)   -- 복합 기본키
);
```

**복합 기본키(composite primary key)** = 여러 열을 묶어서 하나의 키로 쓰는 것.
"이 센서의 · 이 시간대의 · 이 방향" 조합이 유일하다는 뜻이다.

### 🔑 여기서 `direction` 이 `NULL` 금지인 이유

SQL 에서 **`NULL` 은 자기 자신과도 같지 않다.**

```sql
NULL = NULL   →  참이 아니다 (알 수 없음)
```

그래서 `NULL` 이 기본키에 들어가면 "같은 행인지" 판단이 애매해진다.
→ 저장할 때 `COALESCE(direction, '')` 로 **빈 문자열로 바꿔서** 넣는다.

> `COALESCE(a, b)` = "a 가 NULL 이면 b 를 써라".

### ③ `outages` — 장애 이력

```sql
CREATE TABLE outages(
    id          INTEGER PRIMARY KEY AUTOINCREMENT,
    sensor_id   TEXT NOT NULL,
    store       TEXT NOT NULL,
    born_at     TEXT NOT NULL,   -- 끊긴 시각
    resolved_at TEXT NOT NULL    -- 복구된 시각
);
```

`AUTOINCREMENT` = 넣을 때마다 1, 2, 3… 자동으로 번호를 매긴다.
여기서는 **중복을 막을 이유가 없다** — 같은 센서가 여러 번 죽을 수 있고, 그 각각이 별개 사실이다.

### ④ `audit` — 감사 로그

```sql
CREATE TABLE audit(
    id     INTEGER PRIMARY KEY AUTOINCREMENT,
    actor  TEXT NOT NULL,   -- 누가
    role   TEXT NOT NULL,   -- 어떤 권한으로
    action TEXT NOT NULL,   -- 무엇을
    target TEXT NOT NULL,   -- 어디에
    scope  TEXT NOT NULL,   -- 그때 적용된 범위
    at     TEXT NOT NULL    -- 언제
);
```

### 🔑 네 테이블이 **한 파일**에 있다

```
%LOCALAPPDATA%\IoTSensorDashboard\events.db
   ├── events
   ├── events_hourly
   ├── outages
   └── audit
```

> **왜**: 관제실이 기록한 장애를 **대시보드 프로세스가 읽어** SLA 를 계산한다.
> 파일이 나뉘면 그 연결이 끊긴다.

## 4. 데이터가 들어오는 길 (쓰기)

### 한 건 저장

```
CountEvent { SensorId="flir-0001", OccurredAt=09:00:00Z, Count=3, Direction="in" }
        │
        ▼  DedupKey 계산
   "flir-0001|1783414800000|in"
        │
        ▼  INSERT OR IGNORE
   ┌──────────────────────────────────┐
   │ 이 키가 이미 있나?                 │
   │   있음 → 무시,  0 반환 → Duplicate │
   │   없음 → 저장,  1 반환 → Appended  │
   └──────────────────────────────────┘
```

### 여러 건 저장 — 트랜잭션

**트랜잭션(transaction)** = 여러 작업을 **하나의 덩어리**로 묶는 것.

```sql
BEGIN;              -- 시작
  INSERT ...
  INSERT ...
  INSERT ...
COMMIT;             -- 확정 (여기서 진짜로 반영)
```

| 용어 | 뜻 |
|---|---|
| **커밋(commit)** | "확정한다". 이 시점에 변경이 진짜로 반영된다 |
| **롤백(rollback)** | "없던 일로 한다". 중간에 실패하면 전부 되돌린다 |
| **원자성(atomicity)** | 전부 되거나 전부 안 되거나. 절반만 저장된 상태는 없다 |

### 🔑 우리가 트랜잭션을 쓰는 진짜 이유는 **속도**다

커밋할 때마다 DB 는 **"디스크에 확실히 썼는지" 확인**한다(fsync). 이게 비싸다.

```
1건씩  :  [쓰기][확인] [쓰기][확인] [쓰기][확인] …    ← 확인이 매번
묶어서 :  [쓰기][쓰기][쓰기]…[확인]                  ← 확인이 한 번
```

| 방식 | 처리량 |
|---|---|
| 건별 트랜잭션 | 16,941 evt/s |
| 묶음 트랜잭션 | **277,650 evt/s** (16.4배) |

### 파라미터 재사용

```csharp
cmd.CommandText = "INSERT OR IGNORE INTO events(...) VALUES($k,$s,$o,$c,$d);";

var pk = cmd.Parameters.Add("$k", SqliteType.Text);   // 자리를 한 번만 만들고
// …
for (…)
{
    pk.Value = e.DedupKey;                            // 값만 갈아 끼운다
    cmd.ExecuteNonQuery();
}
```

**파라미터(`$k` 같은 자리표시자)를 쓰는 이유는 둘이다.**

1. **속도** — SQL 문을 매번 새로 해석하지 않고 준비된 것을 재사용한다
2. **안전** — 값이 SQL 문법으로 해석되지 않는다 (**SQL 인젝션** 방지)

```
❌ 문자열 이어붙이기 :  "INSERT … VALUES('" + 값 + "')"
                        값에 따옴표가 들어오면 문장이 깨지거나 조작된다
✅ 파라미터          :  값은 언제나 '값'으로만 취급된다
```

> 우리 데이터는 센서에서 오는 외부 입력이다. **밖에서 오는 것은 신뢰하지 않는다.**

## 5. 동시성 — 여러 명이 동시에 접근할 때

### 락(lock) = 자물쇠

같은 데이터를 동시에 고치면 깨지므로, 한 번에 한 명만 들어가게 막는 장치다.

```csharp
lock (_gate)
{
    // 여기는 한 번에 한 스레드만 들어온다
}
```

우리 저장소는 **쓰기를 이 락으로 직렬화**한다 — SQLite 연결은 스레드 안전하지 않기 때문이다.

### 그런데 읽기까지 막히면 곤란하다

```
[기본 모드]
   수집이 쓰는 중 ──▶ 파일 잠금 ──▶ 리포트는 대기
   리포트가 읽는 중 ─▶ 파일 잠금 ──▶ 수집은 대기   ← 이게 진짜 문제
```

실제로 이 사고가 있었다.

> 리포트가 **550만 행을 읽는 동안** 그 긴 읽기가 **WAL 정리를 막아** 수집 쓰기까지 굶었다.

### WAL — Write-Ahead Log (미리 쓰기 기록)

**본 파일을 직접 고치지 않고, 변경분을 별도 파일에 먼저 쌓는 방식.**

```
   쓰기  ──▶  events.db-wal   (변경분이 여기 쌓인다)
                    │
   읽기  ──▶  events.db       (본 파일은 그대로 → 안 막힌다)
                    │
              나중에 합친다
```

> 📖 **비유**: 책을 고칠 때 원본에 바로 쓰지 않고 **포스트잇에 적어 붙여 둔다.**
> 남들은 원본을 계속 읽을 수 있고, 한가할 때 포스트잇을 원본에 옮겨 적는다.

**체크포인트(checkpoint)** = 그 "옮겨 적기".

| 상황 | 방식 | 뜻 |
|---|---|---|
| 한가함 | `TRUNCATE` | 전부 합치고 WAL 파일도 줄인다 |
| 바쁨 | `PASSIVE` | 방해되지 않는 만큼만 합친다 |

### 연결을 두 개 쓴다

```csharp
_write   // 쓰기 전용 — lock 으로 직렬화
_read    // 읽기 전용 — 쓰기 락에 안 막힌다
```

WAL 모드라 이게 가능하다.

## 6. PRAGMA — SQLite 의 설정 스위치

**PRAGMA** = SQLite 에게 "이렇게 동작해라"라고 지시하는 특수 명령.
데이터를 다루는 게 아니라 **DB 자체의 행동**을 바꾼다.

우리가 쓰는 셋:

```sql
PRAGMA auto_vacuum=INCREMENTAL;   -- 지운 공간을 OS 에 돌려줄 수 있게
PRAGMA journal_mode=WAL;          -- 읽기/쓰기가 서로 안 막히게
PRAGMA synchronous=NORMAL;        -- 디스크 확인 횟수를 줄여 삽입을 빠르게
```

### ⚠️ 순서가 중요하다

`auto_vacuum` 은 **빈 DB 에서만** 설정이 먹는다.
테이블이 하나라도 생긴 뒤에 걸면 **조용히 무시된다 — 오류도 안 난다.**

```csharp
_write.Open();
SqliteSchema.ApplyPragmas(_write);   // ① 먼저
SqliteSchema.CreateTables(_write);   // ② 나중
```

이걸 놓치면 나중에 "지우고 있는데 파일이 안 줄어드는" 상태가 되고,
원인을 찾기가 아주 어렵다.

## 7. 시간이 지나면 — 롤업 → 프룬 → 회수

### 왜 필요한가

> 보존·롤업 없이 7시간 돌렸더니 `events.db` 가 **778MB**.
> 건별 INSERT 가 **1,521µs**(정상의 30~100배)로 느려지며 시스템이 **스스로 느려졌다.**
>
> 🔑 **"데이터를 다 보관한다"가 미덕이 아니라 자가 다운의 원인이었다.**

### 3단계

```
① 롤업(rollup)   오래된 원본을 시간대별 합계로 접는다
② 프룬(prune)    접은 원본을 지운다
③ 회수(reclaim)  지운 자리를 OS 에 돌려준다
```

### ① 롤업 — 실제로 일어나는 일

```
[before]  events
  09:00:01  flir-0001  in  3
  09:00:30  flir-0001  in  2
  09:00:55  flir-0001  in  1

[after]   events_hourly
  flir-0001 │ 2026-07-09T09:00:00+00:00 │ in │ count_sum=6 │ event_count=3
```

**3행이 1행이 됐지만 정보는 남았다** — 합계 6, 원본 3건.

SQL 로는 이렇게 한다.

```sql
INSERT INTO events_hourly(...)
SELECT sensor_id,
       strftime('%Y-%m-%dT%H:00:00+00:00', occurred_at) AS hour,  -- 시각 → 시간대
       COALESCE(direction,'') AS dir,
       SUM(count), COUNT(*)                                       -- 집계 함수
  FROM events WHERE rowid IN (SELECT rid FROM _prune_chunk)
 GROUP BY sensor_id, hour, dir                                    -- 묶는 기준
ON CONFLICT(sensor_id, hour, direction) DO UPDATE SET             -- 이미 있으면 더한다
   count_sum   = count_sum   + excluded.count_sum,
   event_count = event_count + excluded.event_count;
```

| 문법 | 뜻 |
|---|---|
| `GROUP BY` | 같은 값끼리 묶는다 |
| `SUM()` · `COUNT()` | 묶인 것들의 합계 · 개수 (**집계 함수**) |
| `strftime()` | 시각을 원하는 모양으로 바꾼다 |
| `ON CONFLICT … DO UPDATE` | **UPSERT** — 없으면 넣고, 있으면 고친다 |
| `excluded` | UPSERT 에서 "넣으려던 값" |

### 🔑 임시 테이블을 쓰는 이유

```sql
CREATE TEMP TABLE _prune_chunk(rid INTEGER PRIMARY KEY);
INSERT INTO _prune_chunk SELECT rowid FROM events WHERE occurred_at < $c LIMIT $n;
```

**롤업과 삭제가 "같은 행"을 봐야 한다.**

각각 조건(`occurred_at < cutoff`)으로 다시 고르면,
그 사이에 새 행이 들어와 **접은 것과 지운 것이 달라진다.**

> 먼저 "이번에 처리할 행 번호"를 확정해 두고, 두 작업이 그 목록만 본다.

**`rowid`** = SQLite 가 모든 행에 자동으로 붙이는 내부 번호. 삽입 순서대로 늘어난다.

### ② 조각으로 나눠서

한 번에 다 하면 안 된다.

> 예전에는 조건에 맞는 **모든 행을 한 트랜잭션**으로 처리했다.
> 폭주 구간(5,000/s)에서는 한 번에 수십만 행이 되고,
> 그동안 **락을 쥐고 있어 수집 워커가 통째로 멈췄다** — 백로그 8만, 화면 수십 초 정지.
>
> **"정리가 수집을 죽이는" 형태**라, 정리 쪽이 양보해야 한다.

그래서 **한 번에 2만 행씩**, 2초 예산 안에서 나눠 처리한다.
조각 사이에 락이 풀리므로 수집 워커가 끼어들 틈이 생긴다.

### ③ 회수 — 지워도 파일이 안 줄어드는 문제

**SQLite 는 `DELETE` 해도 파일 크기를 줄이지 않는다.**
빈 자리를 **free list**(재사용 가능 목록)에 넣을 뿐이다.

```
[페이지] = SQLite 가 파일을 다루는 단위 (보통 4KB)

파일:  ■■■■□□□□■■□□□□□□■■■■     ■ 사용 중   □ 빈 페이지
                                   ↑ 지웠지만 파일 크기는 그대로
```

> 보존창이 **정상 동작하는데도** 파일이 **2,882MB**, 그중 **88% 가 빈 페이지**였다.

| 방법 | 언제 | 무엇 |
|---|---|---|
| **증분 회수**<br/>`PRAGMA incremental_vacuum(N)` | 매 주기 (상시) | 빈 페이지 N개를 OS 에 돌려준다 |
| **전체 재작성**<br/>`VACUUM` | 낭비율 ≥35% **AND** 빈 공간 ≥128MB | 파일을 통째로 다시 쓴다 |

전체 재작성은 **2,882MB → 321MB 에 4.5초**가 걸렸고 그동안 저장소가 멈춘다.
그래서 두 조건을 **모두** 만족할 때만 한다 —
작은 파일에서 35% 는 몇 MB 라 4.5초를 멈출 값어치가 없기 때문이다.

> ⚠️ 그리고 **`VACUUM` 이 `auto_vacuum` 설정을 파일에 다시 굽는다.**
> 실행 전에 PRAGMA 를 다시 걸지 않으면 설정이 풀리고,
> 그때부터 조용히 예전 상태(지워도 안 줄어듦)로 돌아간다.

## 8. 데이터가 나가는 길 (읽기)

### 🔴 여기서 가장 자주 틀린다 — raw 만 보는 것

데이터가 **두 군데**에 나뉘어 있다.

```
        ← 과거                          현재 →
   ┌──────────────────┬──────────────────────┐
   │  events_hourly   │       events         │
   │  (3시간 이전)     │   (최근 3시간)         │
   │  시간대별 합계     │   개별 이벤트          │
   └──────────────────┴──────────────────────┘
```

**두 소스는 시간상 서로소다** — 보존창을 기준으로 딱 갈린다. 겹치지 않는다.

그러니 **더하면 된다.** 안 더하면?

> `events` 만 조회하면 **3시간 이전 데이터가 통째로 사라진 것처럼 보인다.**

### `UNION ALL` — 두 결과를 이어 붙이기

```sql
SELECT k, d, SUM(s), SUM(r) FROM (
    SELECT sensor_id AS k, COALESCE(direction,'') AS d,
           SUM(count) AS s, COUNT(*) AS r
      FROM events WHERE occurred_at >= $c
     GROUP BY k, d
    UNION ALL                                    -- ← 이어 붙인다
    SELECT sensor_id AS k, direction AS d,
           SUM(count_sum) AS s, SUM(event_count) AS r
      FROM events_hourly WHERE hour >= $c
     GROUP BY k, d
) GROUP BY k, d;                                 -- ← 합쳐서 다시 묶는다
```

| 문법 | 뜻 |
|---|---|
| `UNION` | 두 결과를 합치되 **중복을 제거**한다 (느림) |
| `UNION ALL` | 두 결과를 그냥 **이어 붙인다** (빠름) |

우리는 두 소스가 안 겹치는 걸 **알고 있으므로** `UNION ALL` 을 쓴다.

### 총 개수도 마찬가지

```sql
SELECT (SELECT COUNT(*) FROM events)
     + (SELECT COALESCE(SUM(event_count),0) FROM events_hourly);
```

> raw 만 세면 **롤업이 돌 때마다 총계가 줄어드는 것처럼 보인다. 그건 거짓말이다.**

### 타임존 — 저장은 UTC, 표시할 때 보정

```sql
SELECT strftime('%Y-%m-%d', datetime(occurred_at, '+540 minutes')) AS day
```

`+540 minutes` = 9시간 = 한국 시간.

**왜 저장할 때 보정하지 않나**: 관제실을 어느 시간대의 PC 에서 돌리든 **저장된 값은 같아야** 한다.
표시할 때만 보는 사람 기준으로 바꾼다.

```
UTC 2026-07-09 22:00  →  한국에서는 2026-07-10 07:00 (다음 날!)
```

이 보정이 없으면 **"어젯밤 손님"이 "오늘 새벽 손님"으로** 잘못 집계된다.

### 🔒 집계는 반드시 SQL 에서

> 리포트가 **550만 행을 UI 스레드에서 스캔**해 화면이 수십 초 얼어붙었다.

```
❌ 전부 읽어와서 C# 에서 더하기   →  550만 개 객체가 메모리에 올라온다
✅ SQL 에게 시키기               →  결과 몇 줄만 돌아온다
```

집계는 DB 가 가장 잘한다.

## 10. 용어 한눈에

| 용어 | 한 줄 |
|---|---|
| **테이블 / 행 / 열** | 표 / 가로 한 줄 / 세로 칸 |
| **스키마** | 표들의 설계도 |
| **기본키(PK)** | 그 행을 유일하게 식별하는 열. 중복이 안 들어간다 |
| **복합 기본키** | 여러 열을 묶어 만든 키 |
| **NULL** | "값이 없음". 빈 문자열이나 0 과 다르다 |
| **인덱스** | 빨리 찾기 위한 색인. 조회는 빨라지고 삽입은 느려진다 |
| **트랜잭션** | 여러 작업을 하나의 덩어리로 묶는 것 |
| **커밋 / 롤백** | 확정한다 / 없던 일로 한다 |
| **원자적** | 쪼갤 수 없다. 중간에 끼어들 틈이 없다 |
| **락** | 자물쇠. 한 번에 한 명만 들어가게 |
| **WAL** | 변경분을 별도 파일에 먼저 쌓아 읽기/쓰기가 안 싸우게 |
| **체크포인트** | WAL 에 쌓인 것을 본 파일에 합치기 |
| **PRAGMA** | SQLite 의 설정 스위치 |
| **페이지** | SQLite 가 파일을 다루는 단위 (보통 4KB) |
| **free list** | 지워서 비었지만 아직 OS 에 안 돌려준 페이지 목록 |
| **VACUUM** | 파일을 통째로 다시 써서 빈 자리를 없애기 |
| **rowid** | SQLite 가 모든 행에 자동으로 붙이는 내부 번호 |
| **UPSERT** | 없으면 넣고 있으면 고치기 (`ON CONFLICT … DO UPDATE`) |
| **GROUP BY** | 같은 값끼리 묶기 |
| **집계 함수** | 묶인 것들의 합계·개수 (`SUM` · `COUNT`) |
| **UNION ALL** | 두 결과를 이어 붙이기 (중복 제거 안 함) |
| **파라미터 바인딩** | 값을 `$이름` 자리에 넣기. 빠르고 안전하다 |
| **SQL 인젝션** | 값에 SQL 문법을 섞어 넣어 문장을 조작하는 공격 |
| **롤업** | 원본을 집계로 승격시키기 |
| **프룬** | 승격된 원본을 지우기 |
| **보존창** | 원본을 그대로 두는 기간 (우리는 3시간) |

## 11. 이 층이 지키는 약속 다섯

| 약속 | 어떻게 |
|---|---|
| **정확히 1회** | 기본키 + `INSERT OR IGNORE` — DB 가 원자적으로 판정 |
| **한 번 저장한 건 안 바뀐다** | 계약에 수정·삭제 메서드가 없다. `INSERT OR IGNORE` 는 덮어쓰지 않는다 |
| **껐다 켜도 남는다** | exe 위치와 무관한 고정 경로. 세 기록이 같은 파일에 |
| **총계는 변하지 않는다** | 롤업은 삭제가 아니라 승격. 조회는 항상 raw + 롤업 |
| **정리가 수집을 죽이지 않는다** | 조각으로 나눠 처리 · 예산 제한 · 바쁘면 양보 |

> 🧭 다섯 개 전부 **"모르는 것을 아는 것처럼 그리지 마라"**의 저장 층 버전이다.
> 숫자가 새거나, 조용히 바뀌거나, 사라지면 — 그 대시보드는 더 이상 대시보드가 아니다.

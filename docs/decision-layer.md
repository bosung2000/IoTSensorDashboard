# 판정 층 상세 — "숫자가 조용히 틀리는" 자리들

> 4층에서 만든 것을 정리한다.
> 앞의 세 층이 「어떻게 다룰 것인가」였다면, 이 층은 **「무엇이 사실인가」**를 정한다.

---

## 0. 이 층이 정확히 무엇인가

**새로 쓰는 도구가 하나도 없다.** DB 도 네트워크도 화면도 없이, 순수한 계산만 있다.

| # | 무엇 | 대답하는 질문 |
|---|---|---|
| ① **헬스** | 센서 생사 판정 | 얼마나 조용하면 **죽은 것인가** |
| ② **권한** | 조직 트리 · 스코프 | 누가 **어디까지** 볼 수 있는가 |
| ③ **에스컬레이션** | 통지 사다리 | 아무도 안 볼 때 **어디까지 올라가는가** |
| ④ **SLA** | 가동률 · MTTR | 얼마나 **잘 돌았는가** |
| ⑤ **집계** | 시간별 버킷 | 어떤 기준으로 **묶는가** |

### 🔴 그런데 이 층이 가장 위험하다

이 시스템의 **실수는 거의 전부 여기서 났다.**

```
1층 Core     빌드가 막아 준다
2층 Sqlite   틀리면 예외가 난다
3층 Mqtt     안 되면 연결이 끊긴다
4층 판정     ⚠ 아무 일도 안 일어난다 — 숫자만 조용히 틀린다
```

가동률이 100% 로 나와도 프로그램은 잘 돈다. 오류도 없다.
**틀린 걸 알려 줄 사람이 아무도 없다.**

> 🧭 그래서 이 층의 모든 판정을 Core 로 꺼내 **헤드리스 게이트로 못박았다.**
> 판정이 화면 코드에 남아 있으면 자동 검증이 불가능하고,
> **자동 검증이 없는 판정은 조용히 틀린다.**

## 1. 헬스 — 침묵을 어떻게 읽는가 (I5)

### 세 가지 상태

| 상태 | 뜻 | 누가 처리하나 |
|---|---|---|
| `Online` | 최근 수신 있음 | — |
| `Offline` | **보다가 끊긴 것** | 장애 조치 — 알림·에스컬레이션 |
| `Unknown` | **한 번도 신호가 없던 것** | 설치·배선·프로비저닝 문제 |

🔑 **`Offline` 과 `Unknown` 을 합치지 않는다.** 원인이 완전히 달라서 담당자가 다르다.
「끊김」 목록에 미설치 센서가 섞이면 담당자가 헛걸음한다.

### 🔴 분모 — 세 번 연속 틀린 자리

```
❌ 가동률 = 온라인 수 / 지금까지 신호를 받아본 센서 수
✅ 가동률 = 온라인 수 / (있어야 할 명부 ∪ 관측된 센서)
```

**무슨 일이 있었나:**

> 분모가 「관측된 센서」라, 처음부터 죽어 있던 센서가 통째로 빠졌다.
> 1,000대 중 **50대가 무응답인데** 화면은 **950 / 950 = 100%** 를 띄웠다.

이 부류가 가장 찾기 어렵다 — **처음부터 없는 것은 영원히 안 보인다.**
화면에 아무 이상 징후가 없고, 숫자는 오히려 **완벽해 보인다.**

> 🧭 **비율을 그리는 코드를 보면 반드시 분모의 출처를 물을 것.**
> 「있어야 할 것」인가 「이미 본 것」인가.

### 임계는 고정값이 아니다

```
1초마다 쏘는 센서  →  12초 침묵이면 이상하다
1분마다 묶는 센서  →  12초 침묵은 완전히 정상이다
```

**침묵의 뜻은 센서마다 다르다.** 그래서 임계를 **관측된 발신 주기**에서 계산한다.

```
임계 = clamp(관측 주기 × 배수, 바닥, 천장)

오프라인 판정 : 바닥 12초 · 배수 2.5 · 천장 3분
핑 대상 선정  : 바닥 6초  · 배수 1.5 · 천장 2분   ← 더 짧다
```

**핑이 더 짧은 이유**: 오프라인으로 판정하기 **전에 먼저 물어보려고.**

📌 고정 12초였을 때 배치 센서가 계속 오프라인으로 잡혀
**핑 대상이 5대 → 322~742대로 폭증**했다.
「데이터가 곧 생존 증거」라는 설계가, 데이터가 드물어지는 순간
**상시 최대 비용**으로 뒤집힌 것이다.

### 🔑 천장이 반드시 있어야 하는 이유

주기를 **도착에서 배우므로**, 점점 느려지는(죽어가는) 센서는
**「나는 원래 이만큼 조용하다」고 스스로를 가르칠 수 있다.**

천장이 없으면 **센서가 자기 자신에게 면죄부를 준다.**

### 주기 학습의 세 규칙

| 규칙 | 이유 |
|---|---|
| **침묵에서는 안 배운다** | 배우면 죽어가는 센서가 자기 죽음을 정상으로 만든다 |
| **표본 상한 300초** | 한 번의 긴 공백(재연결·백필)이 추정치를 통째로 밀어 올리지 않게 |
| **지수평활 α=0.3** | 빠르게 따라가되 한 번 튄 값에 흔들리지 않게 |

> **지수평활(EMA)** = 새 값을 조금씩 섞어 평균을 갱신하는 방법.
> `새평균 = 옛평균 × 0.7 + 새값 × 0.3`

### 어느 시각을 쓰나

| 시각 | 어디에 |
|---|---|
| **호스트 도착 시각** | **헬스 판정** |
| 기기 시각 | 집계(시간대별 통계) |

📌 기기 시계가 틀려 **미래 시각**이 오면 `지금 − 마지막` 이 계속 음수라
그 센서는 **영원히 온라인**으로 오염된다.

📌 그리고 큐가 깊을 때 **처리 시각**으로 관측하면
이미 죽은 센서가 살아 있는 것으로 보인다 — 하필 부하가 큰 구간에서.
**관제가 가장 필요한 순간에 관제가 거짓말을 한다.**

## 2. 권한 — 모르면 거부 (I4)

### 조직 트리와 서브트리

```
본사 (hq)
├── 수도권본부 (g1)
│   ├── 강남점 (g1-s0)
│   └── …
└── 영남본부 (g2)
    └── …
```

**서브트리** = 그 노드 + 아래 전부. 권한 범위가 이걸로 정의된다.

| 역할 | 볼 수 있는 것 |
|---|---|
| `TotalAdmin` | 전체 |
| `HeadOffice` | 자기 **서브트리** |
| `Group` | 자기 **서브트리** |
| `Store` | **자기 노드만** ⚠ |

### 🔴 `Store` 만 서브트리를 안 쓰는 이유 — 권한 상승 차단

```
매장 역할 계정이 실수로 본부에 배정됨
    ↓
서브트리를 쓰면  →  그 매장 직원이 본부 산하 전 매장을 본다
자기 노드만 쓰면  →  본부 노드 하나만 본다 (아무 데이터도 안 나온다)
```

> 역할 등급과 배정 지점의 정합은 프로비저닝의 책임이지만,
> **Core 는 그걸 믿지 않는다.** 믿지 않는 쪽이 안전하다.

### fail-closed — 모르면 안 보여준다

```
배정이 null / 빈 문자열 / 존재하지 않는 지점
    ↓
❌ 「전부 보임」  → 설정 실수 하나가 전면 노출이 된다
✅ 「아무것도 안 보임」
```

> **fail-closed** = 실패했을 때 **닫히는** 쪽으로 동작한다.
> 반대는 fail-open(열리는 쪽). 보안 경계에서는 언제나 fail-closed 다.

### 왜 예외가 아니라 빈 결과인가

권한 밖 요청에 예외를 던지면 **「그 지점이 존재한다」는 사실**이 새어 나간다.
존재 여부 자체가 정보인 경우가 있다. **빈 결과**가 안전하다.

### 순환 방어

데이터가 잘못돼 `A → B → A` 가 되면 순진한 구현은 **영원히 돈다.**
방문한 노드를 기록하며 순회한다.

## 3. 에스컬레이션 — 방치를 막는 장치

### 소멸 문제

> 1차 통지 한 번으로 끝나면, 점장이 폰을 못 보는 순간 그 장애는 **영원히 방치**된다.
> 화면에는 「통지됨」이라 적혀 있어 **조치가 진행 중인 것처럼 보이고**,
> 아무도 다시 확인하지 않는다.

### 사다리

```
장애 발생
   ↓ 25초 미확인
[1차] 점장          Warning
   ↓ 60초 미확인
[2차] 본부 관리자    Critical
   ↓ 110초 미확인
[3차] 본사 당직      Critical
   ↓ 이후 60초마다 반복
```

> ⚠️ 이 값은 **시연용으로 짧게** 잡은 것이다(3단계가 1분 안에 다 보이도록).
> 실운영 권장: 5분 → 15분 → 30분, 반복 30분.

🔑 **`Critical` 의 뜻**이 「장애가 더 심해졌다」가 아니라
**「아무도 안 보고 있다가 확인됐다」**이다. 같은 장애라도 **방치된 시간**이 길수록 심각해진다.

### 판정 규칙 여섯

| 규칙 | 이유 |
|---|---|
| 복구되면 중단 | 통지할 이유가 사라졌다 |
| 확인(ack)되면 중단 | **사람이 이미 붙었다** |
| 전송 중이면 중단 | 겹쳐 쏘면 같은 장애로 여러 건이 나간다 |
| 백오프 존중 | 매 틱 재시도하면 폭주한다 |
| **한 칸씩만** 올라감 | 건너뛰면 **사다리를 밟은 궤적이 로그에서 사라진다** |
| 최상위는 **반복** | 끝이 있으면 그 뒤로는 다시 조용해진다 |

### 🔴 실패는 승격이 아니다

```
deliveredLevel = 전달에 성공한 최고 단계
                 ↑ 시도만 한 것은 포함하지 않는다
```

📌 시도를 성공으로 세면, 통지가 계속 실패하는데도 사다리가 위로 올라가
**아무도 못 받은 채 끝난다.**

### 생성자가 검사한다

「새 단계 추가 = 한 줄」이 목표인데, **그 한 줄이 틀렸을 때 여기서 잡혀야** 한다.

| 검사 | 안 하면 |
|---|---|
| 레벨 1부터 연속 | 다음 칸을 못 찾아 **멈춘다** |
| 임계 단조 증가 | 앞 칸이 **영원히 발사되지 않는다** |
| 반복 간격 > 0 | **무한 발사** |
| 단계 ≥ 1개 | 아무도 통지받지 못한다 |

안 잡으면 사다리가 **조용히 끊긴다** — 통지가 안 나가는데 오류도 없다.

## 4. 통지 — 밖으로 나가는 호출은 결과를 돌려준다

### 🔴 `void` 가 아닌 이유

📌 **실제 사건**: 화면은 「⚠ 미확인 → 자동 통지됨」이라 쓰는데 담당자는 아무것도 못 받았다.
`Notify` 가 `void` 이고 구현이 예외를 삼켜서 **호출자가 실패를 알 방법이 없었다.**

> **장애를 알리는 장치가 조용히 실패하면, 장애가 두 번 일어나는 셈이다.**
> **드물게 일어나는 채널은 카운터가 유일한 관측점이다.**

일반화하면: **`void` 면 삼킴이 기본값이 된다.**

### 계약에 박아 둔 것

```csharp
NotifyResult Notify(in Notification n);   // 결과를 돌려준다
long Sent { get; }                        // 누적
long Failed { get; }                      // 누적
string? LastError { get; }                // 무엇이
DateTimeOffset? LastFailureAt { get; }    // 언제
```

### 조회도 「전부인 척」하지 않는다

```csharp
EscalationLogView(
    Records,      // 표시 대상
    Total,        // 전체 건수
    Malformed,    // 해석 실패한 줄 수 — 0 이 아니면 로그가 손상된 것
    Undelivered,  // 전달 실패 건수
    Critical);    // 치명 건수 — 표시 상한과 무관한 전체 기준
```

🔑 최근 500건에 치명이 없다고 「치명 0건」이라 쓰면 **거짓말**이다.

### 옛 포맷을 읽는다

로그는 5열 → 6열 → 7열 → 9열로 늘어났다.
**옛 줄을 못 읽어 버리면 「그때는 아무 일도 없었다」로 읽힌다** —
추적 가능성이 존재 이유인 기록에서 그건 최악이다.

> 🔒 그리고 **파일에 쓴 「길이」를 성공의 증거로 쓰지 않는다.**
> 실제로 이 함정에 빠진 적이 있다 — 검증 도구가 파일 길이만 보고 **자기에게 그린을 줬다.**

## 5. SLA — 「측정 불가」를 100%로 쓰지 않는다

### 🔴 가장 크게 거짓말한 숫자

> 종전에는 **장애 이력이 없으면 무조건 가동률 100%** 였다.
> 그래서 **관제실이 꺼져 있었거나 센서가 처음부터 죽어 있던 매장**도 100.000% 로 나왔다.
> 화면이 스스로 「구매 판단 근거」라고 부르는 숫자가 **가장 크게 거짓말**한 것이다.

```
「장애가 없었다」  ≠  「지켜보지 못했다」
```

그래서 `Uptime` 이 **nullable** 이다. `null` = 측정 불가.

### 평균에서도 뺀다

```
❌ null 을 0 으로 보고 평균  → 실제보다 낮게
❌ null 을 1 로 보고 평균    → 실제보다 높게   ← 이게 원래 버그였다
✅ 아예 빼고 계산 + 「측정 불가 N곳」을 함께 표시
```

🔑 **곳수를 반드시 함께 보여준다.** 평균만 보여주면 몇 곳이 빠졌는지 알 수 없고,
그러면 **평균이 다시 거짓말한다.**

### 겹침 병합 (union)

```
센서1  ■■■■■■
센서2      ■■■■■■
센서3   ■■

단순 합산 : 5.5시간  ← 같은 시간을 여러 번 센다
겹침 병합 : 3시간    ✅
```

한 매장에 센서가 여러 대인데 **동시에** 다운되면 단순 합산은 가동률을 실제보다 훨씬 낮게 만든다.

### 창 경계 자르기

```
창 이전에 시작한 장애  →  창 시작부터 센다
아직 안 끝난 장애      →  현재까지 센다
```

창 밖 시간을 세면 가동률이 **음수**가 될 수 있다. `Clamp(0, 1)` 이 최종 방어다.

### 🔴 기본값을 없앤 것도 설계다

```csharp
IReadOnlySet<string> observedStores   // ← 기본값 없음
```

📌 기본값이 있으면 호출부가 **무심코 옛 동작으로 되돌아가** 버그가 **조용히 재발**한다.
필수 인자로 두면 **컴파일러가 막는다.**

> 이건 「방어적 프로그래밍」이 아니라 **회귀를 구조적으로 불가능하게** 만드는 설계다.

## 6. 이 층에서 반복되는 패턴 여섯 — 이게 진짜 배울 것

| # | 패턴 | 구체적 예 |
|---|---|---|
| ① | **비율을 보면 분모의 출처를 묻는다** | 「있어야 할 것」인가 「이미 본 것」인가 |
| ② | **모르면 거부한다 (fail-closed)** | 배정이 없으면 「전부」가 아니라 「아무것도」 |
| ③ | **밖으로 나가는 호출은 결과를 돌려준다** | `void` 면 삼킴이 기본값이 된다 |
| ④ | **「모름」을 값으로 표현한다** | `double?` — 0 도 100% 도 아닌 제3의 상태 |
| ⑤ | **위험한 기본값을 없앤다** | 기본값이 있으면 회귀가 조용히 재발한다 |
| ⑥ | **틀린 설정은 생성 시점에 터뜨린다** | 사다리가 조용히 끊기느니 앱이 안 뜨는 게 낫다 |

> 🧭 여섯 개 전부 **같은 뿌리**다 —
> **"틀렸다는 사실이 드러나게 만든다."**
>
> 이 시스템의 결함은 전부 「안 돌아감」이 아니라 「돌아가는데 조용히 틀림」이었다.
> 그래서 설계의 목표가 **정확성**이 아니라 **틀렸을 때의 가시성**이 된다.

## 8. 이 층이 지키는 약속 다섯

| 약속 | 어떻게 |
|---|---|
| **침묵을 0으로 읽지 않는다** | Offline / Unknown 을 구분하고, 분모는 명부 기준 |
| **경계는 새지 않는다** | fail-closed · Store 는 자기 노드만 · 예외 대신 빈 결과 |
| **방치를 방치하지 않는다** | 사다리가 조직 위로 올라가고 최상위에서 반복 |
| **실패한 통지는 실패로 남는다** | 결과 반환 · 카운터 · 미전달 표시 |
| **못 본 것을 봤다고 하지 않는다** | `Uptime = null` · 평균에서 제외 · 제외 곳수 표시 |

> ## **모르는 것을 아는 것처럼 그리지 마라.**

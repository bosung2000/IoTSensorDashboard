# 사양 공백 대장

명세에 답이 없어서 **내가 정한** 것들을 모아 둔다.

## 왜 이 문서가 필요한가

명세에 없는 것을 만나면 "합리적으로" 결정하고 넘어가기 쉽다.
그런데 **그 합리적 결정이 조용한 오류의 가장 큰 원인**이다 —
결정한 사람은 근거를 알지만, 코드만 보는 다음 사람에게는 그게 그냥 사실처럼 보인다.

그래서 규칙을 이렇게 둔다.

> **명세에 없어서 내가 정한 것은 전부 여기 적는다.**
> 적을 수 없으면 결정하지 않은 것이다.

각 항목은 네 가지를 갖는다: **공백 / 내 판단 / 근거 / 이 판단이 틀렸을 때 벌어지는 일.**
마지막 칸이 핵심이다 — 뒤집혔을 때의 파급을 모르면 그건 판단이 아니라 추측이다.

## G-01 · 저장에 끝내 실패한 이벤트의 판정값

| | |
|---|---|
| **공백** | 배치 저장이 실패해 건별로 재시도했는데 그것마저 실패한 건. 이때 `IngestResult` 를 무엇으로 돌려줄지가 명세에 없다. 판정값은 4종(`Appended`/`Duplicate`/`Rejected`/`Implausible`)으로 고정이라 새 값을 만들 수도 없다. |
| **판단** | `Rejected` 로 보고하고, `StoreFailures` 카운터를 따로 올린다. |
| **근거** | 관측되는 사실은 "저장되지 않았다"이므로 `Rejected` 가 가장 가깝다. 원인(저장소 장애)은 판정 실패와 다르므로 별도 카운터로 구분한다. |
| **틀렸을 때** | — |

### 🔴 실제로 여기서 결함이 났다

처음 구현에서 저장 결과를 `bool` 하나로 돌려줬다. 그러면 상태 셋(**저장됨 / 이미 있음 / 저장 실패**)이
값 둘에 눌려 담기고, **"저장 실패"가 `false` 로 접혀 호출부가 그걸 `Duplicate` 로 읽는다.**

화면에는 **"중복 N건"** 으로 뜬다. 중복은 정상 동작이므로 아무도 이상하게 여기지 않는다.
실제로는 **데이터 손실**인데.

> **"이미 세어 둔 값이라 안 넣었다"와 "넣지 못했다"는 정반대 사실이다.**
> 둘을 같은 색으로 그리면 손실이 영원히 안 보인다.

봉합: 반환 타입을 `IngestResult[]` 로 바꿔 세 상태를 각각 표현.
회귀 테스트 `저장_실패는_중복으로_보고되지_않는다` 로 잠갔다.

**이 결함이 이 문서의 존재 이유다.** 타입 하나를 좁게 잡은 것이 곧바로 "조용한 거짓말"이 됐다.

## G-02 · 단건 수집에서 저장소가 예외를 던질 때

| | |
|---|---|
| **공백** | 명세의 `Ingest` 코드에는 저장 호출을 감싸는 `try` 가 없다. 배치 경로에만 구제 로직이 있다. |
| **판단** | 명세대로 둔다 — 단건 경로에서는 예외를 그대로 올려보낸다. |
| **근거** | 단건 실패의 손실 반경은 1건이다. 구제할 것이 없다. 배치에 구제가 필요한 이유는 **배치화가 손실 반경을 512배로 키우기 때문**이지, 저장 실패 자체를 삼키기 위해서가 아니다. 여기서 예외를 잡으면 그건 구제가 아니라 은폐다. |
| **틀렸을 때** | 워커가 예외로 죽어 수집이 멈춘다. 다만 **멈춘 것은 보인다**(활력 표시등). 조용히 틀리는 것보다 낫다. |

> 처리 책임은 호출자(수집 워커)에게 있다. 워커 층을 만들 때 이 결정을 다시 확인할 것.

## G-03 · Milesight 코덱의 형제 보존

| | |
|---|---|
| **공백** | "한 라인이 깨져도 형제 라인은 보존한다"는 규약이 FLIR 의 `lines` 배열에 대해서만 적혀 있다. Milesight 는 `periodIn`/`periodOut` 이 별도 필드라 같은 규약이 적용되는지 불명확. |
| **판단** | 같은 규약을 적용한다. 방향별로 개별 처리해 한쪽이 깨져도 나머지를 살린다. |
| **근거** | 규약의 취지가 "데이터가 있는데 안 세게 되는 것을 막는다"이고, 그 취지는 페이로드 구조와 무관하다. FLIR 만 살리고 Milesight 는 통째로 버리면 **같은 상황에서 벤더에 따라 수집량이 달라진다.** |
| **틀렸을 때** | 깨진 필드가 있는 Milesight 페이로드에서 이벤트가 더 많이 수집된다. 값 자체는 정상이므로 통계가 틀리지는 않는다. 파급이 작은 쪽으로 붙었다. |

## G-04 · 라우팅 키가 빈 코덱을 등록할 때

| | |
|---|---|
| **공백** | `ISensorCodec.Vendor` 가 빈 문자열인 코덱을 등록하면 어떻게 되는지 명세에 없다. |
| **판단** | 등록 시점에 `ArgumentException`. |
| **근거** | 빈 키로 등록된 코덱은 **영원히 선택되지 않는다**. 등록은 성공했는데 아무 일도 안 일어나고, 오류도 안 난다 — 전형적인 조용한 실패다. 발행 측 미지 벤더를 즉시 터뜨리는 것과 같은 판단이다(우리가 만든 코드의 오타는 즉시 드러나야 한다). |
| **틀렸을 때** | 없다. 정상적인 코덱은 이 검사에 걸리지 않는다. |

## G-05 · 물리 정합 한계가 0 이하일 때

| | |
|---|---|
| **공백** | `maxPlausibleCountPerReading` 은 주입 가능해야 한다고만 적혀 있다. 유효 범위는 없다. |
| **판단** | 0 이하이면 생성자에서 `ArgumentOutOfRangeException`. |
| **근거** | 0 이면 **모든 이벤트가 격리되어 수집이 통째로 멈춘다.** 그런데 오류는 안 난다 — 화면에는 "격리 N건"만 늘어난다. 원인을 찾기 매우 어렵다. |
| **틀렸을 때** | 없다. 0 이하는 어떤 해석으로도 의미가 없다. |

## G-06 · 인메모리 저장소의 스냅샷 순서

| | |
|---|---|
| **공백** | `IEventStore.Snapshot()` 의 순서 보장이 명세에 없다. |
| **판단** | **삽입 순서**를 보존한다. |
| **근거** | 영속 구현이 SQLite 의 내장 `rowid` 로 삽입 순서를 보존하므로, 인메모리도 같아야 두 구현을 바꿔 끼워도 결과가 같다. 순서가 흔들리면 "최초본이 권위"라는 규칙을 눈으로 확인할 수 없다. |
| **틀렸을 때** | 삽입 순서를 전제한 테스트가 영속 구현에서만 통과하거나 그 반대가 된다 — 구현을 바꿔 끼울 수 없게 된다. |

## G-07 · 저장소에서 읽을 때 타임존 offset 을 어떻게 복원할 것인가

| | |
|---|---|
| **공백** | 코덱은 `AdjustToUniversal` 로 전부 UTC 로 통일하라고 명시돼 있다. 그런데 **저장소가 읽을 때**도 같은 규칙인지는 안 적혀 있다. 한편 인수 항목에는 "저장→조회에서 타임존 offset 유지"가 있다. |
| **판단** | **비대칭으로 간다.** 들어올 때(코덱)는 UTC 로 통일하고, 나갈 때(저장소)는 **저장된 offset 을 그대로 복원**한다. |
| **근거** | 두 지점의 역할이 다르다. 코덱은 "제각각인 바깥 표기를 하나로 정리"하는 자리이고, 저장소는 "맡긴 것을 그대로 돌려주는" 자리다. 읽으면서 UTC 로 바꾸면 **저장한 것과 읽은 것이 다른** 저장소가 된다. |
| **틀렸을 때** | 값이 가리키는 순간은 같으므로 통계는 안 틀린다. 대신 왕복(round-trip)이 깨져 "저장소가 데이터를 조용히 바꾼다"는 성질이 생긴다. |

> 🔴 처음 구현에서 저장소 쪽에도 `AdjustToUniversal` 을 붙였다가 인수 항목을 다시 보고 고쳤다.
> 값이 같은 순간을 가리키니 테스트를 대충 짰으면 그냥 통과했을 것이다.
> **"같은 순간"과 "같은 표기"는 다른 요구**라는 걸 놓치기 쉽다.

## G-08 · 보존창 비교가 문자열 비교라는 것

| | |
|---|---|
| **공백** | 명세의 롤업 SQL 이 `WHERE occurred_at < $cutoff` 로 **문자열을 비교**한다. 저장된 값에 서로 다른 offset 이 섞여 있으면 사전순과 시간순이 어긋난다. |
| **판단** | 명세대로 둔다. |
| **근거** | 실제 유입 경로에서는 코덱이 전부 UTC(`+00:00`)로 만들기 때문에 offset 이 섞이지 않는다. offset 이 하나로 고정되면 ISO-8601 은 **사전순 = 시간순**이다. 시각 함수를 태우면 인덱스를 못 타 느려지므로, 이 조건이 성립하는 한 문자열 비교가 옳다. |
| **틀렸을 때** | 코덱을 거치지 않고 다른 offset 으로 직접 저장한 이벤트가 있으면 보존창 판정이 어긋난다. 지금은 그런 경로가 없지만, **새 수집 채널을 만들 때 이 전제를 확인해야 한다.** |

> ⚠️ 이건 "지금은 맞지만 조건부로 맞는" 항목이다. 3층에서 수집 채널을 추가할 때 다시 볼 것.

## G-09 · 집계 조회의 cutoff 가 포함인가 배타인가

| | |
|---|---|
| **공백** | `SumBySensor(cutoff)` 의 cutoff 가 "그 시각 포함"인지 "초과"인지 명세에 없다. |
| **판단** | **포함**(`>=`). |
| **근거** | 롤업의 보존창 경계가 `<`(미만)이므로, 조회를 `>=`(이상)로 두면 두 조건이 **정확히 맞물려 빈틈도 겹침도 없다.** 같은 경계값을 양쪽이 다 버리거나 다 가져가는 일이 없다. |
| **틀렸을 때** | 경계 시각에 정확히 걸친 이벤트 한 건이 조회에서 빠진다. 파급은 작지만, 롤업 경계와 어긋나면 "총계 보존" 검사가 간헐적으로 깨진다. |

## G-10 · 조각 크기가 0 이하일 때

| | |
|---|---|
| **공백** | `RollupAndPrune(cutoff, maxRows)` 의 `maxRows` 유효 범위가 없다. |
| **판단** | 0 이하이면 `ArgumentOutOfRangeException`. |
| **근거** | 0 이면 **아무것도 처리하지 못하는데 호출은 성공한다.** 유지보수 루프가 영원히 헛돌고 DB 는 계속 커지는데, 오류는 안 난다 — 778MB 사고와 똑같은 모양이 된다. |
| **틀렸을 때** | 없다. 0 이하는 어떤 해석으로도 의미가 없다. |

## 확인한 것 — 추측으로 넘어갈 뻔한 자리

명세를 그대로 옮기면서 **"이게 정말 되나?" 싶었던 것**들. 전부 테스트로 확인했다.

| 의심 | 확인 결과 |
|---|---|
| SQLite 의 `strftime` 이 `"o"` 포맷(소수점 7자리 + offset)을 파싱할까? | ✅ 파싱한다. 시간 버킷·일자 버킷 테스트가 통과한다 |
| `datetime(값, '+540 minutes')` 로 타임존 보정이 되나? | ✅ 된다. UTC 22:00 이 KST 기준 다음 날로 넘어간다 |
| `PRAGMA journal_mode=WAL` 이 `ExecuteScalar` 로 실제 적용되나? | ✅ 적용된다 |
| `auto_vacuum` 을 테이블 생성 **전에** 걸어야 한다는 게 사실인가? | ✅ 사실. 신규 DB 가 모드 2(INCREMENTAL)로 나온다 |
| `VACUUM` 이 `auto_vacuum` 설정을 풀어 버리나? | ✅ 그래서 실행 전에 PRAGMA 를 다시 건다. 회수 후에도 모드 2 유지를 확인했다 |

> 🧭 **검증 도구 자신을 의심하라**는 원칙의 적용이다.
> "명세에 그렇게 쓰여 있으니 되겠지"는 확인이 아니다.

## 이 대장을 쓰는 법

- 새 항목은 **결정한 그날** 적는다. 나중에 적으면 근거를 반드시 잊는다.
- **"틀렸을 때" 칸을 못 채우면 아직 결정하지 마라.** 파급을 모르는 채로 고른 것은 판단이 아니라 추측이다.
- 뒤집힌 판단은 **지우지 말고 취소선으로 남긴다.** 왜 그렇게 생각했는지가 다음 사람에게 정보다.
